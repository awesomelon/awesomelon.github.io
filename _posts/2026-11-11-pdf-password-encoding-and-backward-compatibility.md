같은 PDF에 같은 암호를 입력했다. Chrome에서는 정상적으로 열렸지만 PDFBox에서는 암호가 틀렸다는 예외가 발생했다. Acrobat에서는 한글 암호를 붙여넣을 수도 없었다.

처음에는 파일이 손상됐거나 암호가 잘못 전달됐다고 생각했다. 조사해 보니 문자열을 처리하는 방식이 문제였다.

**PDF를 생성할 때와 읽을 때 암호 문자열이 서로 다른 바이트로 변환되고 있었다.**

## 핵심 원인부터 살펴보자

PDFBox에서 암호가 맞지 않은 과정은 세 단계로 정리된다.

1. **PDF 생성:** `hummus`가 한글 암호를 UTF-8 바이트로 처리해 PDF를 생성했다.
2. **PDF 열람:** 이 PDF는 암호화 리비전 3이었고, PDFBox 2.0.37은 리비전 3의 암호를 ISO-8859-1로 인코딩한다.
3. **검증 실패:** 생성과 검증에 사용된 바이트가 달라 올바른 문자열을 입력해도 암호가 일치하지 않았다.

영문과 숫자로만 시험했을 때 문제가 없었던 이유도 여기에 있다. ASCII 문자는 두 인코딩에서 같은 바이트를 쓴다.

다만 바이트 차이로 확인한 것은 PDFBox의 실패 원인뿐이다. Chrome, Acrobat, PDFKit, Poppler가 각각 왜 다른 결과를 보였는지는 아직 다 밝히지 못했다. 그래서 이 글에서는 소스와 파일 분석으로 확인한 사실, 실험에서 관찰한 결과, 아직 확인하지 못한 부분을 나눠 적는다.

## 1. 실제로 어떤 차이가 있었을까?

문제는 한글 암호로 보호된 PDF에서 시작됐다. 문서 서비스 안에서는 정상적으로 열렸고 사용자가 내려받은 PDF도 Chrome에서는 문제없었다. 그런데 서버에서 같은 파일을 PDFBox로 읽으려 하자 암호 불일치 예외가 발생했다.

원인을 좁히기 위해 실제 문서 변환 경로로 PDF를 만들고, 영문·숫자, 한글, 악센트 문자, 한글과 영문을 섞은 암호를 각각 걸어 여러 프로그램에서 열어 봤다.

### 실험에서 관찰한 결과

| 확인한 환경 | 영문·숫자 암호 | 비ASCII 문자 포함 암호 |
|---|---|---|
| PDFBox 2.0.37 | 열림 | 암호 불일치 예외 |
| Adobe Acrobat | 열림 | 한글 붙여넣기 불가, `café`는 입력해도 열리지 않음 |
| macOS PDFKit API | 열림 | `unlock(withPassword:)`가 `false` 반환 |
| Google Chrome | 열림 | 열림 |
| Poppler | 열림 | 열림 |

영문과 숫자로 된 암호는 모든 시험 환경에서 열렸다. 한글이나 악센트 문자가 들어가자 결과가 갈렸다.

이 결과만으로 특정 프로그램에 버그가 있다고 단정할 수는 없다. 파일 생성 과정이 일반적인 처리 방식과 다를 가능성도 있기 때문이다. 또한 이 표는 당시 시험한 파일과 환경에 관한 기록이다. Acrobat과 Chrome의 정확한 버전은 남아 있지 않으며, macOS는 미리보기 앱이 아닌 PDFKit API로 확인했다.

프로그램마다 결과가 다른 이유를 찾기 위해 파일 내부를 조사했다.

## 2. PDF 암호화 방식에서 발견한 단서

당시 PDF 생성에는 `hummus`를 사용하고 있었다. 생성된 PDF의 암호화 사전을 확인하니 다음 값이 나왔다.

| 항목 | 값 | 의미 |
|---|---|---|
| `R` | `3` | 표준 보안 처리 방식의 리비전 |
| `V` | `2` | 암호화 알고리즘 버전 |
| `Length` | `128` | 암호화 키 길이(비트) |

RC4 128비트를 쓰는 구형 방식이다.

암호를 UTF-8 바이트로 넣어 계산한 값은 파일에 저장된 값과 일치했다. hummus가 UTF-8 바이트로 암호화했다는 뜻이다.

### PDFBox가 사용하는 문자 인코딩

PDFBox 2.0.37의 `StandardSecurityHandler` 소스를 살펴봤다. 이 버전은 암호화 리비전에 따라 암호 문자열의 문자셋을 고른다. 기본값은 ISO-8859-1이고 리비전 5와 6에서만 UTF-8을 쓴다.

[PDFBox 2.0.37 StandardSecurityHandler 소스](https://github.com/apache/pdfbox/blob/2.0.37/pdfbox/src/main/java/org/apache/pdfbox/pdmodel/encryption/StandardSecurityHandler.java)

문제의 PDF는 리비전 3이므로 PDFBox는 암호를 ISO-8859-1 바이트로 바꿔 검증한다. 생성할 때는 UTF-8이었으니 바이트가 맞을 수 없다.

### 같은 문자열, 다른 바이트

`abc`와 `café`를 비교하면 차이가 보인다.

| 문자열 | UTF-8 바이트 | ISO-8859-1 바이트 |
|---|---|---|
| `abc` | `61 62 63` | `61 62 63` |
| `café` | `63 61 66 C3 A9` | `63 61 66 E9` |

`abc`는 두 인코딩에서 결과가 같다. 하지만 `café`의 마지막 글자 `é`는 UTF-8에서 2바이트, ISO-8859-1에서 1바이트로 표현된다.

한글은 차이가 더 크다. ISO-8859-1에는 한글이 아예 없다. Java의 `String.getBytes(Charset)`는 이런 문자를 만나도 예외 없이 대체 바이트(`?`)로 바꿔 버린다.

[Java String.getBytes(Charset) 문서](https://docs.oracle.com/javase/8/docs/api/java/lang/String.html#getBytes-java.nio.charset.Charset-)

암호를 생성할 때와 검증할 때 다른 인코딩을 쓰면 사용자가 같은 문자열을 입력해도 검증에 실패할 수 있다. 이번 PDFBox 오류가 그런 경우였다.

### 어디까지 확인됐을까?

**파일과 소스로 확인한 사실**

- 문제가 된 PDF의 암호화 사전은 `R=3`, `V=2`, `Length=128`이었다.
- 해당 PDF의 암호화 결과는 UTF-8로 변환한 암호 바이트와 일치했다.
- PDFBox 2.0.37은 리비전 3의 암호를 ISO-8859-1로 인코딩한다.
- 따라서 이 파일을 PDFBox에서 열 때 생성 시점과 검증 시점의 암호 바이트가 달라진다.

**실험으로 관찰한 결과**

- PDFBox와 PDFKit API에서는 비ASCII 암호가 설정된 시험 파일을 열지 못했다.
- Chrome과 Poppler에서는 같은 방식으로 만든 시험 파일을 열었다.
- Acrobat에서는 한글 붙여넣기가 불가능했고 `café` 암호 검증에도 실패했다.

**아직 확인하지 못한 부분**

- Chrome과 Poppler가 내부에서 어떤 문자 인코딩이나 호환성 처리를 사용했는지
- Acrobat과 PDFKit의 실패가 PDFBox와 정확히 같은 내부 원인에서 발생했는지
- 각 프로그램의 다른 버전에서도 동일한 결과가 나타나는지

## 3. 기존 PDF를 다시 열 수는 없을까?

원인을 확인한 뒤에는 이미 생성된 PDF를 처리할 방법을 검토했다. 사용자에게 배포된 PDF도 있어서 전부 다시 암호화할 수는 없었다. 대신 PDFBox에 전달하는 암호를 변환하는 방법을 시험했다.

원래 UTF-8 바이트를 ISO-8859-1 문자열로 옮겨 담은 뒤 PDFBox에 전달하는 방식이다. 예를 들어 `café`를 UTF-8로 인코딩하면 다음 바이트가 나온다.

```text
63 61 66 C3 A9
```

이 바이트를 ISO-8859-1 문자열로 해석하면 `cafÃ©`가 된다. PDFBox에 이 문자열을 전달하면 내부에서 다시 ISO-8859-1로 인코딩하고, 그 결과는 처음의 UTF-8 바이트와 같다.

```text
63 61 66 C3 A9
```

문자열은 달라졌지만 최종 바이트는 복원된 셈이다.

### 실험 결과

이 방식으로 한글·악센트·혼합 암호 시험 파일을 모두 열었고 첫 페이지 렌더링도 성공했다.

다만 범용 해결책은 아니다. 처음부터 ISO-8859-1로 암호화한 PDF에 같은 변환을 적용하면 오히려 검증에 실패할 수 있다. 그래서 입력한 암호로 먼저 열어 보고, 실패하면 hummus로 만든 과거 파일에 한해 변환한 암호로 다시 시도하는 편이 안전하다.

또한 이 방법은 서버가 PDFBox로 문서를 처리할 때만 도움이 된다. 이미 내려받은 PDF를 Acrobat에서 직접 여는 문제는 해결하지 못한다.

## 4. AES-256으로 바꾸면 해결될까?

인코딩 문제를 우회하는 대신 암호화 방식을 바꾸는 방법도 있다. 기존 파일은 RC4 128비트와 리비전 3을 사용했다. 리비전 6은 암호를 UTF-8로 처리하도록 규정하므로, AES-256·리비전 6으로 바꾸면 이번 인코딩 불일치는 피할 수 있다.

PDFBox로 AES-256·리비전 6 시험 파일을 만들어 확인했다.

### 실험 결과

| 확인한 환경 | 비ASCII 암호 결과 |
|---|---|
| PDFBox | 열림 |
| Poppler | 열림 |
| macOS PDFKit API | 열리지 않음 |
| Acrobat | 미확인 |
| Chrome | 미확인 |

PDFBox와 Poppler에서는 정상적으로 열렸지만 같은 조사 환경의 PDFKit API에서는 여전히 실패했다. 적어도 조사한 환경에서는 암호화 방식을 바꿔도 모든 프로그램에서 같은 결과를 얻지 못했다.

그렇다고 AES-256이나 리비전 6 자체에 호환성 문제가 있다고 볼 수는 없다. PDFKit이 실패한 원인은 추가로 분석하지 않았고 Acrobat과 Chrome에서도 시험하지 못했다.

암호화 방식을 바꾸는 것만으로 모든 대상 뷰어에서 비ASCII 암호가 작동한다고 보장할 근거는 부족했다. 알고리즘 교체와 뷰어 호환성 검증은 따로 다뤄야 했다.

## 5. 새 암호는 어디까지 허용해야 할까?

그래서 새로 설정하는 암호의 문자 범위를 제한하기로 했다. 허용 범위는 **U+0020부터 U+007E까지**, 공백을 포함한 출력 가능한 ASCII 문자다.

| 문자 종류 | 허용 여부 |
|---|---|
| 영문 대소문자 | 허용 |
| 숫자 | 허용 |
| 기호 | 허용 |
| 일반 공백 | 허용 |
| 한글 | 거절 |
| 악센트 문자 `é` | 거절 |
| 이모지 | 거절 |
| 탭과 줄바꿈 | 거절 |

이 범위의 문자는 UTF-8과 ISO-8859-1에서 같은 바이트로 표현되므로 이번에 확인한 인코딩 불일치를 피할 수 있다.

물론 ASCII만 허용한다고 모든 PDF 뷰어에서 정상적으로 열린다는 보장은 없다. 암호화 방식, 뷰어 버전, 구현에 따라 다른 문제가 생길 수 있다. 이 정책은 모든 PDF 환경을 검증한 결과가 아니라 확인된 호환성 위험을 줄이기 위한 선택이다.

문자 호환성과 암호 보안성도 구분해야 한다. 한글이나 이모지를 막는다고 암호가 더 안전해지지는 않는다. 암호 길이와 복잡도, 암호화 알고리즘의 안전성은 별도로 검토할 문제다.

### 기존 한글 암호는 어떻게 할까?

새 암호를 제한하는 일과 기존 문서를 계속 열 수 있게 하는 일은 다르다. 이미 한글 암호가 설정된 문서에까지 새 문자 정책을 적용하면, 사용자는 올바른 기존 암호를 알고 있어도 문서를 열지 못할 수 있다.

그래서 암호를 새로 설정하는 과정과 기존 암호를 검증하는 과정을 구분했다. 새로 설정하는 암호에는 ASCII 문자 정책을 적용하고, 기존 한글 암호로 서비스 안에서 문서를 열거나 서명하는 기능은 유지한다. 암호를 바꾸지 않고 다른 설정만 수정할 때도 기존 값을 보존한다.

다만 기존 한글 암호를 최종 PDF에 새로 적용하려는 경우에는 별도 검사가 필요하다. 서비스 안에서 쓸 수 있는 암호라고 해서 외부 PDF 뷰어와도 호환된다는 보장은 없기 때문이다.

이미 배포된 PDF는 새 정책으로 바뀌지 않으므로, 과거 파일은 생성 방식에 맞춰 따로 처리해야 한다.

이번 변경으로 기존 파일 문제가 모두 풀린 것은 아니다. 새 문서에서 같은 문제가 반복되지 않게 막고, 기존 문서는 계속 열 수 있게 한 것이다.

## 6. PDF 호환성을 어떻게 검증해야 할까?

돌아보면 시험 조건에 중요한 빈틈이 있었다. 영문과 숫자로만 시험해서는 인코딩 차이가 드러나지 않는다. PDF를 생성한 라이브러리로 다시 열어 보는 시험도 충분하지 않다. 실제 사용자는 Chrome이나 Acrobat을 쓸 수 있고, 서버에서는 PDFBox나 Poppler처럼 다른 라이브러리로 같은 파일을 처리할 수 있다.

PDF 암호 호환성은 프로그램 하나에서 열리는지가 아니라, 생성 도구와 열람 도구의 조합마다 확인해야 한다. 확인할 항목은 다음과 같다.

1. **암호 문자 범위:** 영문·숫자뿐 아니라 한글, 악센트 문자, 혼합 문자열을 시험한다.
2. **암호화 방식:** PDF의 암호화 리비전과 알고리즘, 문자열 인코딩 방식을 확인한다.
3. **생성 프로그램:** 실제 배포 경로에서 생성된 PDF를 사용한다.
4. **열람 프로그램:** Chrome, Acrobat, PDFKit, PDFBox, Poppler 등 지원 대상에서 확인한다.
5. **기존 파일:** 새로운 방식으로 생성한 PDF뿐 아니라 과거에 배포된 파일도 검증한다.

암호 불일치 오류가 났다면 사용자의 입력을 의심하기 전에 생성 시점과 검증 시점의 바이트부터 비교해 볼 필요가 있다. 이번 사례에서는 그 차이가 원인을 설명하는 결정적인 단서였다.

## 마치며

같은 한글 암호를 썼는데도 PDF 뷰어마다 결과가 달랐다. 추적해 보니 PDF 생성에는 UTF-8 바이트가 쓰였고 PDFBox 2.0.37은 해당 리비전에서 암호를 ISO-8859-1로 처리했다. 바이트를 복원하는 방식으로 기존 시험 파일도 다시 열 수 있었다. 다만 Chrome과 Poppler가 왜 열었는지, Acrobat과 PDFKit이 어디서 실패했는지는 끝내 확인하지 못했다.

**같은 문자열이 반드시 같은 바이트를 뜻하지는 않는다.**

PDF 암호 호환성은 암호화 알고리즘만으로 결정되지 않는다. 문자열이 어떤 바이트로 변환되는지, 그리고 파일을 읽는 프로그램이 그 바이트를 어떻게 처리하는지까지 맞아야 한다. 평소엔 보이지 않던 차이가 한글 암호 하나로 드러난 셈이다.
