하루는 개발팀에게 CS가 들어왔습니다. 고객이 엑셀 다운로드하려고 하는데 브라우저가 죽는다는 CS였습니다.

확인 결과 DB에서 데이터를 읽어온 후 클라이언트 단에서 엑셀 파일을 생성하고 있는 것이었습니다.

기존에는 `3만 건` 이하의 데이터를 만들고 있었고, 이슈가 된 데이터 수를 확인하니 `18만 건의 데이터`로 확인되었습니다.

## 엑셀 파일을 만들다가 브라우저가 죽다니?

XLSX 파일의 형식은 OOXML(Open Office XML)입니다. OOXML 이름 그대로 XML을 기반으로 데이터를 저장하고 표현합니다.

XLSX 파일은 여러 XML 파일을 포함하는 폴더를 압축한 형태입니다.

> 확장자를 `.zip`으로 변경 후 압축을 해제하면 아래와 같은 파일 구조를 볼 수 있습니다.
{: .prompt-tip }

![2023-08-05-image2](2023-08-05-image2.png)
_XLSX 파일의 내부 구조_

row의 정보는 `{sheetName}.xml` 파일에 저장되는데 이 파일에는 필요한 정보 외에 XML 오버헤드도 굉장히 많기 때문에 몇 만의 row 정보를 한 번에 메모리에 올리면 `OOM`이 발생할 가능성이 큽니다.

따라서 stream 처리가 되어야 합니다.

### 기존 구조의 문제점

기존 구조는 아래와 같았습니다. 데이터를 읽어와서 클라이언트(브라우저)에서 바로 만드는 것이었습니다.

![2023-08-05-image1](2023-08-05-image1.png)
_기존 엑셀 다운로드 구조_

기존의 데이터 수량으로는 브라우저에서 엑셀 데이터를 만드는 것이 가능했을지 몰라도 이제는 변경해야 한다고 판단하고 개선 작업을 진행했습니다.

> 이 서비스를 사용하는 유저는 10명 미만으로 아래 방법들은 그것을 고려하여 작은 볼륨으로 작업한 것입니다.
{: .prompt-info }

## 첫 번째 개선: 서버 사이드 Stream 처리

엑셀 파일을 생성하는 서버에서 엑셀 다운로드 요청이 왔을 때, 빈 엑셀 파일을 우선 생성하고 DB에서 데이터를 Stream으로 읽어와 row 하나씩 엑셀 파일에 append하는 방식입니다.

엑셀 데이터가 완료되면 클라우드 스토리지에 업로드 후 사용자에게 엑셀 파일을 내려 줍니다.

![2023-08-05-image3](2023-08-05-image3.png)
_서버 사이드 Stream 처리 구조_

### 개선 효과

**장점:**
- 브라우저 OOM 문제 해결
- 메모리 효율적인 처리

**단점:**
- 데이터가 많아질수록 사용자가 엑셀이 다운받아질 동안 대기해야하는 문제가 발생

> 브라우저가 죽는 현상은 해결되었으나, 사용자 경험 측면에서 추가 개선이 필요했습니다.
{: .prompt-warning }

## 두 번째 개선: 비동기 처리 도입

위의 문제를 해결하기 위해 비동기 처리를 했습니다.

클라이언트에서 엑셀 파일 요청을 보내면 서버에선 대기열에 쌓아두고 `Status 200`으로 클라이언트에 상태를 내려줍니다.

서버에선 대기열에 쌓인 요청들을 첫 번째 개선 방법과 같이 처리를 합니다.

이런 방식으로 하면 유저는 로딩화면을 계속 볼 필요없이 다른 작업을 하다가 엑셀 다운로드 페이지에서 생성된 엑셀을 다운로드하면 됩니다.

![2023-08-05-image4](2023-08-05-image4.png)
_비동기 처리 구조_

### 개선 효과

**장점:**
- 사용자는 대기 없이 즉시 응답 받음
- 백그라운드에서 파일 생성
- 다른 작업을 병행할 수 있음

**구현 포인트:**
- 작업 대기열(Queue) 관리
- 작업 상태 추적
- 완료된 파일 다운로드 페이지 제공

> 비동기 처리를 통해 사용자 경험을 크게 개선할 수 있었습니다.
{: .prompt-tip }

## 정리

대용량 엑셀 다운로드 문제 해결 과정:

### 문제 분석

| 항목 | 내용 |
|:---|:---|
| **초기 문제** | 18만 건 데이터 처리 시 브라우저 OOM |
| **근본 원인** | 클라이언트에서 대용량 XML 데이터를 메모리에 한 번에 로드 |
| **기존 처리량** | 3만 건 이하 |

### 해결 방안

**1단계: 서버 사이드 Stream 처리**
- DB → Stream 읽기 → Row별 Append → 클라우드 저장소 업로드
- 메모리 효율성 확보
- 브라우저 부담 제거

**2단계: 비동기 처리**
- 요청 즉시 응답 (작업 대기열 등록)
- 백그라운드 파일 생성
- 완료 후 다운로드 페이지에서 파일 제공

### 아키텍처 변화
```
[Before]
클라이언트 → DB 조회 → 클라이언트 엑셀 생성 → 다운로드
           (OOM 발생)

[After - 1단계]
클라이언트 → 서버 → DB Stream → 서버 엑셀 생성 → 클라우드 저장 → 다운로드
                    (대기 시간 발생)

[After - 2단계]
클라이언트 → 서버 (즉시 응답)
             ↓
           Queue → 백그라운드 처리 → 완료 알림 → 다운로드 페이지
```

### 고려사항

이 해결 방안은 소규모 사용자(10명 미만)를 위한 것입니다. 더 큰 규모의 서비스라면 다음을 추가로 고려해야 합니다:

- 분산 작업 큐 시스템 (Redis Queue, RabbitMQ 등)
- 작업 우선순위 관리
- 파일 생성 실패 시 재시도 로직
- 생성된 파일의 자동 삭제 정책
- 동시 작업 수 제한
