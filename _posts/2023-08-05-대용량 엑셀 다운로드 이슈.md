고객이 엑셀 다운로드하려고 하는데 브라우저가 죽는다는 CS가 들어왔습니다.

확인 결과 DB에서 데이터를 읽어온 후 클라이언트 단에서 엑셀 파일을 생성하고 있었습니다. 기존에는 3만 건 이하의 데이터를 처리했는데, 이슈가 된 데이터 수는 18만 건이었습니다.

---

## 왜 브라우저가 죽는가?

XLSX는 OOXML(Office Open XML) 형식으로, 워크시트와 서식 등의 정보를 담은 여러 파일을 ZIP 패키지로 묶은 형태입니다.

> 확장자를 `.zip`으로 변경 후 압축을 해제하면 내부 구조를 볼 수 있습니다.
{: .prompt-tip }

![2023-08-05-image2](2023-08-05-image2.png)
_XLSX 파일의 내부 구조_

행과 셀 정보는 보통 `xl/worksheets/sheet1.xml` 같은 워크시트 파일에 저장됩니다. 파일명이 화면에 보이는 시트 이름과 같은 것은 아닙니다. 클라이언트에서 파일을 만들 때는 조회 데이터, 라이브러리의 내부 객체, XML과 압축 버퍼 등이 메모리를 사용하므로 데이터가 커지면 OOM이 발생할 수 있습니다. 다만 행 수만으로 한계를 정할 수는 없고, 셀의 수와 내용, 라이브러리 구현에 따라 메모리 사용량이 달라집니다.

![2023-08-05-image1](2023-08-05-image1.png)
_기존 엑셀 다운로드 구조_

---

## 첫 번째 개선: 서버 사이드 Stream 처리

엑셀 다운로드 요청이 오면 DB에서 데이터를 Stream으로 읽고, 행을 하나씩 서버에서 생성하는 엑셀 파일에 기록합니다. 완료되면 클라우드 스토리지에 업로드 후 사용자에게 내려줍니다. 이때 서버의 메모리 사용도 줄이려면 엑셀 라이브러리가 스트리밍 쓰기를 지원하는지 확인해야 합니다. DB 조회만 스트리밍하고 모든 행을 메모리에 보관한다면 서버에서도 메모리 문제가 생길 수 있어요.

![2023-08-05-image3](2023-08-05-image3.png)
_서버 사이드 Stream 처리 구조_

브라우저 OOM 문제는 해결됐지만 데이터가 많아질수록 사용자 대기 시간이 길어지는 문제가 생겼어요.

---

## 두 번째 개선: 비동기 처리 도입

클라이언트가 엑셀 파일 생성을 요청하면 서버는 작업을 대기열에 등록하고 HTTP 200으로 즉시 응답합니다. 등록된 작업은 백그라운드에서 처리합니다.

유저는 로딩 화면을 계속 볼 필요 없이 다른 작업을 하다가 엑셀 다운로드 페이지에서 생성된 파일을 다운로드하면 됩니다.

## 정리

**아키텍처 변화:**
```
[Before]
클라이언트 → DB 조회 → 클라이언트 엑셀 생성 (OOM 발생)

[After - 1단계]
클라이언트 → 서버 → DB Stream → 서버 엑셀 생성 → 클라우드 저장 → 다운로드

[After - 2단계]
클라이언트 → 서버 (즉시 응답) → Queue → 백그라운드 처리 → 다운로드 페이지
```

이 해결 방안은 소규모 사용자(10명 미만)를 위한 것입니다. 더 큰 규모라면 분산 작업 큐 시스템, 작업 우선순위 관리, 재시도 로직, 파일 자동 삭제 정책 등을 추가로 고려해야 해요.
