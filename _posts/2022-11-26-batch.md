## 배치(Batch) 작업 어디까지 해봤니?

서비스를 구축하다 보면 많은 양의 데이터를 **일괄적으로 변경**하거나 **삭제** 등의 처리를 해야 할 순간이 옵니다.
이런 작업을 **트래픽이 몰리는 시간대**에 하게 되면 서비스에 치명적일 수도 있고, 잘못된다면 서비스 전체가 셧다운 되는 악몽을 꾸게 될 수도 있습니다.

> 이때 해야 하는 것이 **배치(Batch) 작업**입니다.
{: .prompt-tip }

### 배치 작업이란?

배치 작업은 데이터를 **실시간으로 처리하는 게 아니라**, 일괄적으로 모아서 **한 번에 처리**하는 작업을 의미합니다.

| 특징 | 설명 |
|:---|:---|
| **일괄 처리** | 데이터를 모아서 한 번에 처리 |
| **비동기 실행** | 사용자에게 빠른 응답이 필요하지 않은 작업에 적합 |
| **스케줄링** | 트래픽이 적은 시간대에 실행 |

예를 들어, **은행의 정산 작업**의 경우 배치 작업을 통해 일괄처리를 수행합니다.

> 이번 글에선 `MongoDB` + `Node.js`를 활용한 **배치 작업 테스트 결과**를 공유하고자 합니다.
{: .prompt-info }

## Take1 🎥

![2022-11-26-image1](2022-11-26-image1.png)

간단한 코드입니다.
`TestA` 컬렉션에서 데이터를 가져와 `TestB` 컬렉션의 document를 **하나씩 update** 하는 코드입니다.

> 실제 운영 중인 서비스에선 여러 비즈니스 로직이 들어가겠지만, 큰 틀에서 보면 이것과 비슷한 패턴이 많습니다.
{: .prompt-info }

문제가 크게 없어 보이는 코드이지만, 실제로 이 코드를 실행해 보면 어떨까요?

### 결과

![2022-11-26-image2](2022-11-26-image2.png)

> **Heap 메모리 부족**으로 프로세스가 죽었습니다. 😱
{: .prompt-danger }

### Node.js 메모리 제한

Node.js는 버전별로 아래와 같이 사용할 수 있는 **기본 메모리 제한**이 있습니다.

![2022-11-26-image3](2022-11-26-image3.png)

메모리 제한을 늘리려면 아래 커맨드를 사용할 수 있습니다:

```bash
node --max-old-space-size=<memory>
```

> 하지만 이것은 **근본적인 해결책이 아닙니다**.  
> 코드 상에서 **메모리 누수**가 발생하는 부분을 찾거나, **메모리를 많이 잡아먹는 로직**이 있는지 먼저 살펴봐야 합니다.
{: .prompt-warning }

### 원인 분석

살펴보니 `TestA`, `TestB` 컬렉션에 document가 **각각 50만 개**가 존재했습니다.

![2022-11-26-image4](2022-11-26-image4.png)

데이터양을 확인한 후 Take1의 테스트 코드를 보면 문제가 보입니다:

- 50만 개의 데이터를 가져오는 것도 문제지만...
- **50만 번**의 `updateOne` 호출은 더 큰 문제입니다!

![2022-11-26-image5](2022-11-26-image5.png)

### 해결책: BulkWrite

이럴 때 사용하면 좋은 MongoDB의 메서드가 [**bulkWrite**](https://j-ho.dev/feature-3/) 입니다.

이름이 아주 명확하죠? 😎

> **BulkWrite**는 이름 그대로 DB에 **쓰기 작업을 대량으로** 해주는 메서드입니다.
{: .prompt-tip }

| 특징 | 설명 |
|:---|:---|
| **순차 처리** | 기본적으로 배열로 들어온 쓰기 작업을 순차 처리 |
| **병렬 처리** | 옵션을 통해 병렬 처리도 가능 |

그렇다면 바로 `BulkWrite`를 적용한 후 테스트 코드를 실행해 보겠습니다.

40%면 아직 여유가 있다고 생각하실 수 있지만:
- update 로직이 **조금만 더 복잡해지거나**
- 데이터가 **더 많아진다면**

문제가 생길 여지가 있습니다.

> DB의 사양을 늘리면 되지 않느냐고 하실 수도 있지만... (`give me the money 💰`)
{: .prompt-info }

### 근본적인 문제

역시 문제는 **많은 양의 데이터를 한 번에 처리**하려고 하니까 생기는 문제인 듯합니다.

![2022-11-26-image8](2022-11-26-image8.png)

50만 개의 데이터를 **읽기만 하는 것**으로도 많은 시간이 걸립니다.

> 그렇다면 **몇 개씩 나눠서 처리**를 한다면 어떨까요?
{: .prompt-tip }

## Take3 🎥

![2022-11-26-image9](2022-11-26-image9.png)

**반복문이 추가**됐습니다. 데이터를 **10,000개씩** 가져와 쓰기 작업을 하는 코드로 변경했습니다.

| 방식 | 설명 |
|:---|:---|
| **분할 처리** | 50만 개 → 10,000개씩 50번 |
| **검색 횟수** | 증가하지만 안정적 |

### 결과

![2022-11-26-image10](2022-11-26-image10.png)

| 항목 | Take2 | Take3 |
|:---|:---:|:---:|
| **처리 시간** | 1분 19초 | 1분 25초 |
| **CPU 사용률** | ~40% | ~22% |

실행 시간은 **1분 25초**로, 50만 개의 데이터를 한 번에 처리하는 것과 **비슷한 처리 시간**이 나타났습니다.

한 번에 데이터를 처리하는 것과 나눠서 처리하는 것에서 **속도의 차이는 거의 없어 보입니다만...**

![2022-11-26-image11](2022-11-26-image11.png)

> CPU 사용률을 보면 **22% 정도**로, Take2의 **반절 정도**의 사용률을 보여줍니다.  
> **훨씬 안정적**입니다! 👍
{: .prompt-tip }

### 문제점

확실히 좋아 보이는 처리 방법이지만 **단점**은 존재합니다.

> **나눠서 처리할 데이터양을 정하는 것이 어렵습니다.**
{: .prompt-warning }

| 현재 상황 | 문제점 |
|:---|:---|
| 테스트 데이터 | 용량이 작아 만 개로 지정 가능 |
| 운영 데이터 | 훨씬 더 큰 메모리 사용 |

예를 들어, 지금 테스트에 사용하고 있는 MongoDB는 쿼리에 응답하는 데이터의 **최대 메모리가 40MB**입니다.

> 따라서 만 개의 데이터가 **40MB를 넘어버린다면**, MongoDB는 **쿼리에 응답하지 못할 것**입니다.
{: .prompt-danger }

### 해결책: Stream

저는 해결 방법을 **Stream**으로 생각했습니다.

DB에서 SELECT를 해올 때 **Stream으로 데이터를 가져와서 하나씩 처리**한다면:
- 처리 시간은 **훨씬 오래 걸리겠지만**
- **안정적**일 것입니다

## Take4 🎥

`cursor` 명령어가 추가됐습니다.

> **cursor**는 쿼리에 대한 결과를 document로 반환하지 않고, **cursor로 반환**하는 명령어입니다.

`cursor`에 대한 자세한 내용은 아래 첨부해둔 링크에서 참고해 주세요.

### 결과

## 결론

지금까지 여러 코드를 테스트해 보았습니다.

`Take3`과 `Take4`가 괜찮은 결과를 보였지만, **어느 방법으로 선택할 것인지는 서비스마다 다를 것**입니다.

| 요구사항 | 추천 방식 |
|:---|:---|
| 리소스를 더 쓰더라도 **빠른 실행 시간**을 원한다면 | **Take3** (분할 처리) |
| 실행 시간이 오래 걸리더라도 **리소스를 절약**하길 원한다면 | **Take4** (Stream 처리) |

> **핵심은 서비스 특성에 맞는 방식을 선택하는 것**입니다.
