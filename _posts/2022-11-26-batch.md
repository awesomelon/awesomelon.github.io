서비스를 구축하다 보면 많은 양의 데이터를 일괄적으로 변경하거나 삭제 등의 처리를 해야 할 순간이 옵니다. 이런 작업을 트래픽이 몰리는 시간대에 하게 되면 서비스에 치명적일 수도 있고, 잘못된다면 서비스 전체가 셧다운 되는 악몽을 꾸게 될 수도 있죠.

이때 고려할 수 있는 방법이 배치(Batch) 작업입니다. 배치 작업은 데이터를 실시간으로 처리하는 게 아니라, 일괄적으로 모아서 한 번에 처리하는 작업을 의미합니다. 예를 들어 은행의 정산 작업의 경우 배치 작업을 통해 일괄처리를 수행합니다.

이번 글에선 MongoDB + Node.js로 배치 작업을 테스트한 결과를 공유합니다.

---

## 테스트 환경

- Cloud: Tencent Cloud CVM
- CPU/RAM: 2core / 2GB
- Database: MongoDB WT 4.2.19
- Runtime: Node.js v14.19.0, NestJs

DB Schema:
```text
TestA: { name: string }
TestB: { name: string, aId: string }
```

---

## Take1

![2022-11-26-image1](2022-11-26-image1.png)

간단한 코드입니다. TestA 컬렉션 전체를 읽고, 각 document에 대응하는 TestB의 `updateOne` 작업을 만든 뒤 `Promise.all`로 한꺼번에 실행하는 코드입니다.

### 결과

![2022-11-26-image2](2022-11-26-image2.png)

Heap 메모리 부족으로 프로세스가 죽었어요.

Node.js의 V8 힙에는 기본 크기 제한이 있으며, 버전과 실행 환경에 따라 달라집니다.

![2022-11-26-image3](2022-11-26-image3.png)

`node --max-old-space-size=<MiB>`로 V8의 old space 크기 제한을 늘릴 수 있지만 이것은 프로세스 전체 메모리 제한이 아니며, 근본적인 해결책도 아닙니다. 코드 상에서 메모리 누수가 발생하는 부분을 찾거나 메모리를 많이 잡아먹는 로직이 있는지 먼저 살펴봐야 합니다.

TestA, TestB 컬렉션에 document가 각각 50만 개가 존재했습니다.

![2022-11-26-image4](2022-11-26-image4.png)

50만 개의 데이터를 한 번에 보관하면서 대량의 `updateOne` 작업까지 동시에 준비하고 실행하는 구조가 메모리 사용을 키울 수 있어요.

이럴 때 사용하면 좋은 MongoDB의 메서드가 [bulkWrite](https://j-ho.dev/feature-3/)입니다. BulkWrite는 DB에 쓰기 작업을 대량으로 해주는 메서드입니다.

## Take2

![2022-11-26-image6](2022-11-26-image6.png)

Take1 코드에서 BulkWrite만 추가된 코드입니다.

### 결과

![2022-11-26-image7](2022-11-26-image7.png)

이번에는 문제없이 50만 개의 document가 update 되었습니다. 처리 시간 1분 19초, CPU 사용률 ~40%.

1분 19초는 나쁘지 않은 속도이지만 로직이 실행되는 동안 DB CPU가 40%가량 치솟는 것이 문제입니다. update 로직이 조금만 더 복잡해지거나 데이터가 더 많아진다면 문제가 생길 여지가 있어요.

한 번에 처리하는 양을 줄이면 부하도 줄일 수 있을지 확인해봤습니다. 다만 이 결과만으로 CPU 부하의 원인을 하나로 단정할 수는 없습니다.

![2022-11-26-image8](2022-11-26-image8.png)

그렇다면 몇 개씩 나눠서 처리를 한다면 어떨까요?

---

## Take3

![2022-11-26-image9](2022-11-26-image9.png)

반복문이 추가됐습니다. 데이터를 10,000개씩 가져와 쓰기 작업을 하는 코드로 변경했습니다.

### 결과

![2022-11-26-image10](2022-11-26-image10.png)

실행 시간은 1분 25초로, 50만 개의 데이터를 한 번에 처리하는 것과 비슷한 처리 시간이 나타났습니다.

![2022-11-26-image11](2022-11-26-image11.png)

CPU 사용률을 보면 22% 정도로, Take2의 반절 정도의 사용률을 보여줍니다. 훨씬 안정적이에요.

단점은 나눠서 처리할 데이터양을 정하는 것이 어렵습니다. 테스트 데이터는 용량이 작아 만 개로 지정 가능하지만 운영 데이터는 훨씬 더 큰 메모리를 사용합니다.

MongoDB에 쿼리 결과 전체를 40MB로 제한하는 일반 규칙은 없습니다. BSON 문서 하나의 크기 제한은 16MiB이며, 큰 조회 결과는 커서의 여러 배치로 나눠 전달할 수 있습니다. 여기서 주의할 점은 애플리케이션이 받은 문서와 쓰기 작업 배열을 메모리에 얼마나 보관하느냐입니다.

저는 해결 방법으로 Stream을 생각했습니다. 조회 결과를 순차적으로 가져오면 메모리에 한꺼번에 보관하는 양을 줄일 수 있을 것 같았습니다.

## Take4

![2022-11-26-image12](2022-11-26-image12.png)

Mongoose의 `cursor()`가 추가됐습니다. 조회 결과 전체를 배열로 받는 대신 `QueryCursor`로 문서를 순차적으로 읽고, 쓰기는 여전히 10,000개씩 모아 `bulkWrite`로 처리합니다.

위 이미지의 코드는 마지막에 10,000개 미만으로 남은 작업을 쓰지 않는 문제가 있습니다. `eachAsync()`가 끝나면 남은 작업도 `bulkWrite`로 저장해야 합니다.

```typescript
if (tasks.length > 0) {
  await this.testBModel.bulkWrite(tasks);
}
```

### 결과

![2022-11-26-image13](2022-11-26-image13.png)

시간은 11분 55초로 많이 걸렸습니다. 하지만 CPU 사용률은 엄청나게 줄어든 것을 확인할 수 있어요.

---

## 결론

이 테스트에서는 Take3과 Take4가 괜찮은 결과를 보였지만, 어느 방법을 선택할지는 서비스마다 다를 것입니다. 커서를 사용한다고 본질적으로 느려지는 것은 아니며, 읽기 배치 크기와 쓰기 방식, 인덱스 등에 따라 결과가 달라집니다. Take3의 `skip()` 방식도 데이터가 늘면 비용이 커질 수 있고, 작업 중 원본 데이터가 변경되면 누락이나 중복을 고려해야 합니다.

- 리소스를 더 쓰더라도 빠른 실행 시간을 원한다면: **Take3** (분할 처리)
- 실행 시간이 오래 걸리더라도 리소스를 절약하길 원한다면: **Take4** (Stream 처리)

결국 서비스 특성에 맞는 방식을 고르는 게 중요합니다.
