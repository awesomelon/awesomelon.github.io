브레드크럼(Breadcrumbs)은 현재 페이지가 사이트 어디에 속하는지 보여주고 상위로 이동하게 하는 내비게이션이다. ["브레드크럼은 죽었다"는 글](https://webdesignerdepot.com/breadcrumbs-are-dead-in-web-design/)을 보고, 나는 이 사망 선고가 성급하다고 느꼈다.

다만 익숙한 패턴이라는 이유로 무조건 넣자는 주장에도 동의하지 않는다. 중요한 질문은 **사용자가 현재 위치를 이해하거나 상위 범주로 이동해야 하는데, 다른 내비게이션만으로 충분한가**다.

![브레드크럼 예시](2025-03-27-image1.jpg)
_상위 계층과 현재 위치를 함께 보여주는 브레드크럼_

## 먼저 세 가지를 구분하기

화면 위에 경로처럼 나열된 UI라도 역할은 서로 다를 수 있다.

| 종류 | 보여주는 것 | 예시 |
|:---|:---|:---|
| 위치 기반 | 현재 페이지의 정보 계층 | 제품 → 노트북 → 모델 A |
| 이력 기반 | 사용자가 실제로 지나온 경로 | 검색 결과 → 모델 A |
| 속성·필터 표시 | 선택한 탐색 조건 | 노트북 · 14인치 · 재고 있음 |

`홈 → 제품 → 노트북`은 브라우저 방문 기록이 아니다. [W3C 브레드크럼 패턴](https://www.w3.org/WAI/ARIA/apg/patterns/breadcrumb/)에 설명돼 있듯, 사용자가 검색 엔진에서 곧바로 제품 상세로 들어왔어도 상위 계층으로 올라가 비슷한 제품을 둘러볼 수 있게 돕는 데 목적이 있다.

반면 "검색 결과로 돌아가기"는 검색어·필터·페이지 번호를 복원하는 동작이다. 필요하다면 위치 기반 브레드크럼과 별도 링크로 제공하는 편이 명확하다. 두 역할을 섞으면 같은 제품으로 이어지는 경로가 방문 순서마다 달라져 구조를 이해하기 어려울 수 있다.

## 무엇이 있으면 가치가 커질까

검색이 좋아져 중간 계층을 거치지 않더라도 브레드크럼은 쓸모가 있다. 오히려 상세 페이지로 처음 들어왔을 때 "이 제품이 어떤 범주에 속하지?"라는 질문에 답할 수 있다.

다만 깊이가 3단계 이상이면 반드시 넣어야 한다는 기준은 없다. 링크가 실제로 의미 있는 상위 목적지로 이어지는지가 중요하다.

| 화면의 상황 | 판단 |
|:---|:---|
| 깊은 제품 분류·기술 문서, 상세 페이지 직접 유입 | 상위 탐색을 돕는 브레드크럼을 검토 |
| 화면이 한두 개뿐인 단순한 서비스 | 제목과 주 내비게이션으로 충분한지 먼저 확인 |
| 여러 카테고리에 속하는 같은 항목 | 대표 경로 또는 맥락별 경로 정책을 먼저 정의 |
| 검색·필터 중심 업무 목록 | 브레드크럼보다 목록 상태 복원이 더 중요할 수 있음 |
| 단계별 작성·결제 화면 | 정보 계층보다 진행 단계 표시가 더 적합할 수 있음 |

URL을 `/`로 나눠 그대로 표시한다고 정보 구조가 완성되지는 않는다. `/app/items/123/edit`에서 `app`, `123`을 사용자에게 보여줄 이유는 없다. 라우트와 리소스 이름을 바탕으로 사람이 이해할 수 있는 경로를 구성해야 한다.

여러 범주에 속한 제품은 더 신중하게 다뤄야 한다. 같은 모델이 "업무용"과 "가벼운 노트북"에 속한다면 하나의 절대 경로만 정답이라고 말할 수 없다. 대표 경로 정책을 일관되게 적용하고, 검색에서 바로 들어온 경우 어떤 경로를 보여줄지도 정해 두면 사용자가 위치를 예측하기 쉬워진다.

## 접근성은 작은 HTML에서 시작한다

다음은 위치 기반 브레드크럼 마크업 예시다.

```html
<nav aria-label="현재 위치">
  <ol class="breadcrumbs">
    <li><a href="/">홈</a></li>
    <li>
      <span aria-hidden="true">/</span>
      <a href="/products/">제품</a>
    </li>
    <li>
      <span aria-hidden="true">/</span>
      <span aria-current="page">노트북</span>
    </li>
  </ol>
</nav>
```

`nav`로 내비게이션 영역을 감싸고 레이블로 목적을 알린다. 목록으로 항목 순서를 나타내고 구분 기호는 `aria-hidden`으로 숨기며, 기본 링크를 쓰면 별도 키보드 이동 규칙을 짜지 않아도 된다.

[W3C ARIA 브레드크럼 지침](https://www.w3.org/WAI/ARIA/apg/patterns/breadcrumb/)에서는 현재 페이지가 링크일 때 `aria-current="page"`를 붙이도록 안내하고, 위 예시처럼 텍스트일 때는 선택 사항이다. 결국 **ARIA 속성을 많이 붙이는 것과 접근성을 잘 구현하는 것은 별개 문제**다.

SPA에서도 링크 주소가 의미 있어야 한다. 상위 항목을 누르면 예상한 목록이 나오는지, 키보드 초점이 화면에 보이는지, 긴 제목을 확대해도 탐색을 방해하지 않는지 확인해야 한다.

## 모바일에서는 남길 정보를 먼저 고르기

긴 경로를 무조건 한 줄에 밀어 넣으면 글자가 너무 작아지거나 링크를 누르기 어려워진다. 두 줄로 감싸거나 중간 항목만 접거나 바로 위 부모만 제공하는 방식 중 실제 과제에 맞게 고르면 된다.

부모 하나만 남긴다면 `뒤로` 대신 `노트북 목록`처럼 목적지를 드러내는 레이블이 낫다. 브라우저에서 방문한 이전 페이지와 상위 계층은 다를 수 있기 때문이다.

중간 항목을 접는 버튼에는 무엇을 여는지 알 수 있는 이름을 주고 펼침 상태를 전달해야 한다. 접기 UI 때문에 조작이 늘어나는 부담도 함께 살펴봐야 한다.

## 화면의 브레드크럼과 검색용 데이터는 별개다

위 HTML은 사람과 보조 기술을 위한 내비게이션이라, HTML에 `aria-current`를 붙였다고 Google 검색용 `BreadcrumbList` JSON-LD까지 자동으로 따라오지는 않는다.

또 [Google BreadcrumbList 문서](https://developers.google.com/search/docs/appearance/structured-data/breadcrumb)를 보면 구조화된 데이터를 넣었다고 검색 결과 노출이나 순위 상승까지 보장되지는 않는다.

한편 [Google 모바일 URL 표시 변경](https://developers.google.com/search/blog/2025/01/simplifying-breadcrumbs)에서 Google은 2025년 1월부터 모바일 검색 결과의 URL 표시에서는 브레드크럼을 없애고 도메인만 보여주겠다고 밝혔다(데스크톱에는 유지). **검색 결과 표시 정책과 사이트 안에서 사용자가 쓰는 탐색 가치는 따로 봐야 한다.**

## 넣은 뒤에는 클릭률보다 과제 성공을 보기

브레드크럼 클릭률이 낮다고 실패한 UI는 아니다. 사용자는 클릭하지 않고도 현재 위치를 확인할 수 있고, 반대로 클릭이 너무 많다면 주 메뉴가 혼란스러워 우회하고 있는 신호일 수도 있다.

사용자가 구체적인 과제를 해결할 수 있는지 확인하고 싶다. 상세 페이지로 바로 들어온 사용자가 상위 범주를 설명할 수 있는지, 비슷한 항목을 찾을 수 있는지, 검색에서 왔을 때 목록으로 돌아가는 경로를 혼동하지 않는지 살펴보는 편이 좋다. 키보드와 좁은 화면에서도 같은 일을 할 수 있는지 함께 확인한다.

나는 브레드크럼을 사이트 완성도를 보여주는 장식으로 넣고 싶지는 않다. **실제 계층과 유용한 상위 목적지가 있고, 사용자가 그 관계를 이해할 필요가 있을 때** 쓰면 된다. 그 조건이 없다면 브레드크럼부터 만들기보다 정보 구조와 주 내비게이션을 먼저 정리하는 편이 낫다.
