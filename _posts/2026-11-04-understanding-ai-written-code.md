요구사항을 적어 넘기면 AI 에이전트가 코드를 짜고 테스트를 돌린 뒤 오류까지 고쳐 온다. 예전 같으면 문서를 뒤지고 직접 구현하느라 반나절은 썼을 작업이 몇 분 만에 PR 초안으로 나온다. 손으로 키보드를 두드리는 시간은 확실히 줄었다.

그런데 내가 그 코드를 얼마나 이해하고 있는지는 별개의 문제다.

최근 Addy Osmani의 글을 읽으며 이 질문이 계속 남았다. AI를 덜 쓰자는 이야기가 아니라, 에이전트를 적극적으로 쓰면서도 판단의 주도권을 놓치지 않는 방법에 가깝다.

## AI가 정확해질수록 검토는 어려워진다

AI가 짠 코드가 엉성하던 시절에는 오히려 문제를 찾기 쉬웠다. 잘못된 문법이나 없는 API 호출, 어색한 로직이 바로 눈에 띄었기 때문이다. 요즘은 다르다.

코드 구조가 자연스럽고 변수명도 적절하며 테스트까지 통과했다면 검토의 깊이가 얕아지기 쉽다. 수백 줄짜리 diff를 열어도 대충 훑고 넘어가기 십상이다. 특히 직전 작업에서 연달아 좋은 결과를 냈다면 이번에도 괜찮겠거니 믿고 넘기기 쉽다. 매번 모든 코드를 한 줄씩 같은 깊이로 읽을 수 없는 현실도 있다.

**하지만 코드가 돌아간다는 사실과 내가 그 코드를 이해하고 있다는 사실은 다르다.**

가령 사용자 인증 기능에서 비밀번호 입력 실패 횟수를 제한하는 작업을 AI에게 맡겼다고 하자. 구현도 끝났고 테스트도 통과했다. 그런데 실패 횟수를 사용자별로 세는지, IP별로 세는지, 여러 요청이 동시에 들어올 때도 제한이 유지되는지는 테스트 결과 화면만 봐서는 모른다.

문법과 정상 동작 너머로 코드 안에 어떤 가정과 결정이 숨어 있는지 들여다봐야 하는 이유다.

## 인지적 위임과 인지적 항복의 차이

Addy Osmani는 AI를 활용하는 방식을 세 가지 상태로 설명한다.

- **Cognitive Offloading(인지적 위임)**: 작업은 AI에게 맡기지만 결과에 대한 판단과 책임은 유지한다.
- **Deferral(판단 유예)**: AI의 결과를 충분히 검토하지 않은 채 다음 작업의 전제로 사용한다.
- **Cognitive Surrender(인지적 항복)**: AI의 결론을 자신의 판단처럼 받아들이고 더 이상 검증할 필요를 느끼지 않는다.

이 가운데 가장 경계해야 할 상태는 인지적 항복이다. 처음에는 AI가 만든 코드를 꼼꼼하게 읽다가도, 손에 익으면 핵심 부분만 확인하고, 나중에는 바뀐 파일 목록과 테스트 통과 여부만 보게 된다. 그러다 어느 날 내가 승인한 코드가 왜 이렇게 짜였는지 설명하지 못하는 순간이 온다.

이때 쌓이는 것이 **이해 부채(Comprehension Debt)**다.

이해 부채는 코드보다 팀과 내 머릿속에 남는다. 저장소는 깔끔하고 테스트도 통과한다. 하지만 새 요구사항이 들어왔을 때 왜 이런 구조가 만들어졌는지, 어디를 고쳐야 안전할지 감이 잡히지 않는다.

물론 거대한 코드베이스를 전부 외우고 있을 수는 없다. 대신 필요한 시점에 해당 영역이 어떻게 굴러가고 왜 그렇게 설계됐는지 다시 추적할 수 있어야 한다. 코드를 암기하는 능력보다 맥락을 복원해 내는 감각이 더 중요하다고 생각한다.

## 코드 작성의 병목은 검증으로 이동하고 있다

예전에는 구현 자체에 시간을 제일 많이 썼다. 이제 AI가 코드를 빠르게 뽑아 주면서 오히려 읽고 검증하는 데 쓰는 시간이 더 무거워졌다.

테스트 통과는 테스트가 적은 조건을 통과했다는 뜻일 뿐이다. 만약 AI가 요구사항을 잘못 짚고 그 잘못된 가정을 그대로 테스트로 옮겼다면, 모든 테스트가 통과해도 제품 동작은 어긋난다.

그래서 "테스트도 짜서 돌려줘"라고만 해서는 부족하다. 작업을 맡기기 전에 무엇을 확인해야 하는지 기준부터 잡아야 한다.

예를 들어 다음과 같이 구분할 수 있다.

- 기능이 정상적으로 동작하는가?
- 경계 조건과 실패 상황을 처리하는가?
- 기존 기능에 영향을 주지 않는가?
- 요구사항에 명시되지 않은 동작을 AI가 임의로 결정하지 않았는가?
- 테스트가 확인하지 못한 부분은 무엇인가?

물론 UI 문구 하나 고치는 일과 인증 정책을 손보는 일에 같은 무게를 둘 수는 없다. 깨졌을 때의 파급력을 보고 검증 강도를 조절하는 편이 합리적이다.

앞으로는 코드를 얼마나 많이 뽑았는지보다 그 변경을 얼마나 자신 있게 설명할 수 있는지를 더 중요하게 봐야 하지 않을까.

## 좋은 프롬프트보다 문제를 이해하는 일이 먼저다
{: id="좋은-프롬프트보다-중요한-것은-문제에-대한-이해다" }

AI를 잘 쓰려면 프롬프트 기술을 익혀야 한다는 이야기를 자주 듣는다. 하지만 막상 써보면 좋은 프롬프트는 문장 다듬기에서 나오지 않는다. 내가 풀려는 문제를 제대로 파악하고 있어야 요청도 선명해진다.

요구사항이 흐릿한 채로 넘기면 AI는 빈칸을 제 나름의 추측으로 메워 그럴듯한 결과를 가져온다. 겉보기에 기능은 완성됐지만 원래 풀려던 문제와는 조금 다른 물건이 만들어질 수 있다.

Addy Osmani는 이러한 문제를 **의도 부채(Intent Debt)**라는 개념으로 설명한다. 내가 적어 주지 않은 목적과 제약조건을 AI가 임의로 해석해 채워 넣은 흔적이 구현물에 남는 것이다.

이를 줄이려면 구현에 앞서 최소한 네 가지를 생각해야 한다.

1. **목적**: 이 기능을 왜 만드는가?
2. **범위**: 무엇을 변경하고 무엇은 변경하지 않는가?
3. **제약**: 반드시 지켜야 하는 정책이나 기술적 조건은 무엇인가?
4. **완료 기준**: 어떤 상태가 되어야 작업이 끝났다고 판단할 수 있는가?

AI는 답을 빠르게 내놓지만 그 속도가 질문의 정확함까지 대신해 주지는 않는다. 그래서 구현을 요청하기 전에 내 가설부터 짧게라도 적어 두는 습관을 들이려 한다.

처음부터 정답을 맞힐 수는 없어도 내 생각과 비교할 기준이 있어야 AI의 분석과 근거를 통해 잘못된 방향을 바로잡을 수 있다.

## AI에게 무엇을 맡기고, 무엇을 직접 판단할 것인가

모든 코드를 손으로 분석하고 모든 결정을 혼자 내릴 수는 없다. 반복 작업에서 벗어나 더 중요한 문제에 집중하려고 AI를 쓰는 것이니, **작업 실행과 판단을 나눠 볼 필요가 있다.**

코드 초안 작성이나 반복적인 리팩터링, 테스트 생성, 문서 정리는 얼마든지 맡길 수 있다. 반면 무슨 문제를 풀지, 우리 시스템 구조에 어떤 설계가 맞는지, 어느 정도 위험까지 감수할지는 내가 직접 관여해 결정해야 한다.

물론 설계를 저울질하거나 놓친 예외를 짚어내는 과정에서도 AI는 유용한 협업 상대가 된다. 다만 그 제안을 받아들일지 결정하고 나중에 이유를 설명할 몫은 내 쪽에 남긴다.

작업 전에는 해결하려는 문제와 가설, 제약조건, 완료 기준을 정리한다. 작업 중에는 AI가 구현과 자동 검증을 진행하되, 중요한 설계 변경이나 요구사항 해석은 중간에 확인한다. 작업 후에는 완료 보고만 읽고 넘기지 않고 실제 diff와 테스트를 열어 AI가 스스로 결정한 부분이 없는지 살핀다.

이렇게 챙긴다고 해서 모든 실수를 걸러낼 수는 없겠지만, 적어도 AI가 만든 결과를 무작정 따라가는 일은 줄어든다.

## AI 시대에도 개발자의 사고력은 필요하다

AI가 지금보다 훨씬 정확하고 빠르게 코드를 짜는 날이 올 것이다. 그때가 되면 직접 코드를 치고 디버깅하는 감각을 예전만큼 붙잡고 있어야 할지 고민이 된다.

그래도 AI가 짠 코드가 맞는지 틀리는지 알아채려면 기반 기술에 대한 이해가 바닥에 깔려 있어야 한다. 내가 전혀 모르는 영역에서는 AI의 설명이 타당한지조차 가려내기 어렵기 때문이다.

그래서 모든 구현을 직접 하지는 않더라도 중요한 기술 역량은 의식적으로 유지해 두려 한다.

가끔은 AI 없이 문제를 해결해 보고, 익숙하지 않은 개념을 직접 익히고, AI가 내놓은 해결책의 빈틈을 일부러 찾아보는 과정도 필요하다.

AI보다 코딩을 더 잘하려는 게 아니라, AI의 결과를 제대로 판단할 눈을 잃지 않기 위해서다.

## 마치며

예전에는 손으로 빠르게 구현하는 능력이 큰 비중을 차지했다. 앞으로는 문제를 정의하고 적절한 해법을 골라 검증하는 힘이 더 크게 작용할 것이다. 에이전트가 구현 시간을 줄여 준 만큼, 아낀 시간을 어디에 써서 내 사고력을 지킬지 고민해야 한다. 나 역시 AI를 얼마나 잘 다루는지만큼이나 작업 과정에서 어떤 판단을 직접 붙잡고 있는지 돌아보게 된다.

결국 남는 질문은 AI가 몇 줄을 작성했느냐보다 훨씬 단순하다.

**AI가 작성한 결과에 대해 나는 무엇을 이해했고, 어떤 근거로 그것이 옳다고 판단했는가?**

작업은 얼마든지 위임할 수 있다. 다만 그 결과를 팀과 제품 앞에서 책임지는 일까지 무심코 넘기지는 않으려 한다.
