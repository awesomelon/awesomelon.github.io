AI 코딩 에이전트에게 기능 하나를 맡겼다. 빌드가 되고 테스트도 통과한다. 화면에서 요청한 동작도 확인했다. 이때 리뷰를 끝내도 될까?

최근 Codex 스킬의 코드 리뷰 기준을 다듬으며 이 질문을 자주 생각했다. 지금 맞게 동작하는지 확인한 뒤에는, 다음에 같은 규칙을 바꿀 때 어디를 고쳐야 하는지도 살펴봐야 한다.

이 글에서 말하는 코드 품질은 보안·성능까지 합친 종합 점수가 아니라 **이번 변경이 유지보수에 미치는 영향**이다. 어떤 동작을 확인했고, 같은 이유로 다시 수정할 때 무엇을 더 찾아야 하는지 구분해 보려 한다.

## 테스트 통과가 말해주는 범위

빌드는 결과물을 생성할 수 있는지, 타입 검사는 선언된 타입과 코드가 맞는지, 테스트는 지정한 조건에서 기대한 결과가 나오는지 확인한다. 어느 하나도 검사하지 않은 입력과 사용자 흐름까지 보장하지는 않는다.

여기서 두 질문을 나눠야 한다.

1. **정확성:** 요구한 동작이 실제로 맞는가? 실패·권한·경계 조건까지 필요한 범위에서 검증했는가?
2. **유지보수성:** 같은 종류의 다음 변경에서 수정 위치와 영향 범위를 파악하기 쉬운가?

첫 번째 질문을 확인한 뒤에도 두 번째 질문은 남는다. 지금은 올바른 결과를 내지만 같은 규칙을 여러 곳에 복사한 코드가 그 예다. 테스트가 놓친 버그를 발견했다면 정확성 문제로 먼저 다룬다.

## 화면 두 곳에서 모두 맞게 보이지만

다음은 실제 프로젝트 코드가 아닌 **설명을 위한 가상 사례**다.

문서 목록과 상세 화면에 새 상태 `EXPIRED`를 '만료됨'으로 표시해야 한다고 해보자. 프로젝트에는 문서 상태의 표시 문구를 결정하는 `getDocumentStatusLabel()`이 이미 있다. 에이전트가 두 화면을 각각 수정한다.

```tsx
// DocumentList.tsx와 DocumentDetail.tsx에 각각 추가된 코드
const label =
  document.status === 'EXPIRED'
    ? '만료됨'
    : getDocumentStatusLabel(document.status);
```

두 화면에서 `EXPIRED`가 '만료됨'으로 보이고 기존 상태도 그대로 표시되는지 테스트했다면, 확인한 범위의 동작은 맞다. 하지만 상태 문구를 결정하는 경로가 기존 함수와 두 화면의 조건문으로 나뉘었다.

나중에 '만료됨'을 '기한 만료'로 바꾸려면 두 화면을 찾아야 한다. 다른 화면에도 같은 조건이 추가됐는지 검색해야 할 수도 있다. 테스트가 통과해도 다음 수정의 탐색 범위는 넓어질 수 있다.

두 화면이 같은 문구를 사용해야 한다면 기존 `getDocumentStatusLabel()`에 새 상태를 추가하는 작은 수정으로 충분하다. 새 추상화를 만들 이유는 없다. 화면마다 다른 문구가 필요한 요구사항이라면 결론이 달라진다. 코드를 합치기 전에 두 조건문이 정말 같은 표시 규칙인지 확인해야 한다.

## '코드 품질 8점'보다 필요한 것

[Earendil의 코드 품질 측정 글](https://earendil.com/posts/measuring-code-sloppiness/)도 동작의 정답을 확인하는 일과 중복·복잡성을 평가하는 일을 구분한다. 코드 줄 수 같은 지표는 조사할 단서가 되지만, 숫자만 줄이는 방향으로 쓰면 원래 알고 싶었던 품질을 놓칠 수 있다.

AI에게 '10점 만점에 몇 점인가'를 묻는다면 어떤 코드를 왜 고쳐야 하는지 알기 어렵다. 나는 변경 전후를 놓고 다음 네 가지를 확인하겠다.

| 질문 | 확인할 증거 |
|---|---|
| 같은 규칙이 늘어났는가? | 새 조건문과 기존 표시 함수가 같은 결정을 하는지 |
| 책임이 흩어졌는가? | 상태 문구를 결정하는 코드가 어느 파일에 있는지 |
| 다음 변경 범위가 넓어졌는가? | 문구 하나를 바꿀 때 함께 수정해야 할 위치 |
| 새 복잡성이 필요한가? | 추가된 추상화·설정값·분기를 요구하는 실제 사용처 |

이 표는 자동 채점표가 아니다. 수정 파일이 늘어도 책임을 올바르게 나눈 결과일 수 있고, 코드 줄 수가 줄어도 읽기 어려운 분기로 압축했을 수 있다. 숫자는 조사할 위치를 알려준다. 실제 판단에는 기존 코드와 요구사항이 필요하다.

위 사례의 리뷰 결과라면 다음과 같이 적을 수 있다.

> `DocumentList.tsx`와 `DocumentDetail.tsx`에 동일한 `EXPIRED` 조건이 추가됐다. 표시 문구를 바꿀 때 두 파일을 수정해야 한다. 이미 사용 중인 `getDocumentStatusLabel()`에 상태를 추가하면 한곳에서 바꿀 수 있다.

위치, 후속 비용, 수정안이 모두 드러난다.

## AI에게는 판정보다 분석을 맡긴다

에이전트에게는 기존 구현과 변경된 사용처를 찾게 할 수 있다. 리뷰 의견에는 '과잉설계'나 '아키텍처 위반'이라는 이름보다 해당 코드가 어디에 있고, 다음 변경에서 어떤 일을 더 하게 되는지가 필요하다.

리뷰를 요청한다면 이렇게 쓰겠다.

```text
이 diff를 검토해줘.

1. 먼저 요구사항 대비 동작 오류와 누락된 검증을 확인해줘.
2. 그다음 기존 코드와 비교해 중복된 규칙, 흐려진 책임 경계,
   불필요한 추상화가 생겼는지 확인해줘.
3. 각 지적에는 변경 위치, 근거, 어떤 다음 변경에서 문제가 되는지,
   가장 작은 수정안을 적어줘.
4. 확인하지 못한 사용처와 추정은 구분하고, 근거가 약하면 지적하지 마.

점수는 매기지 마. 문제가 없다면 없다고 말해줘.
```

리뷰 결과가 나오면 지적한 사용처와 요구사항을 확인한다. 에이전트가 기존 함수를 놓쳤거나 두 화면의 문구가 의도적으로 다르다면 분석이 틀릴 수 있다.

## 작은 변경에서 멈출 기준

위 사례라면 기존 함수에 `EXPIRED`를 추가하는 것으로 끝낼 수 있다. 새 상태를 위해 별도의 공통 상태 엔진이나 설정 체계를 만들 필요는 없다. 리뷰에서 찾은 문제의 크기에 맞춰 수정한다.

리뷰를 마칠 때는 세 가지만 확인하고 싶다.

- 요청한 동작과 중요한 경계 조건이 검증됐는가?
- 새 표시 규칙을 기존 책임 위치에 두고, 같은 결정을 불필요하게 복사하지 않았는가?
- 제안한 품질 수정이 실제 다음 변경의 탐색·수정 범위를 줄이는가?

답이 모호하면 실제 사용처를 더 확인한다. 테스트 통과 후에도 리뷰가 해야 할 일은 남는다. **이번 변경 때문에 다음 문구 변경에서 몇 군데를 찾아야 하는지**처럼 구체적으로 물으면 고칠 문제와 멈출 지점이 보인다.
