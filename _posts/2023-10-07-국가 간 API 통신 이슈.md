서비스를 오픈하고 얼마 지나지 않아 고객에게 화면이 너무 늦게 뜬다는 CS가 들어왔습니다.

처음엔 서버 코드의 이슈인지 파악하기 위해 API들의 실행 시간을 체크했습니다. 하지만 API 상에는 문제가 없었고 DB slow query도 아니었습니다.

혹시 앱 페이지를 로드할 때 이미지를 가져오는 부분이 문제일지 모른다고 생각했습니다. 이미지들은 서울 리전의 스토리지에 업로드되어 있고 앱에선 그 스토리지를 직접 바라보고 있었기 때문입니다. HTTP/1.1에서는 브라우저가 같은 출처로 여는 동시 연결 수를 제한하므로, 이미지 요청이 많으면 대기 시간이 생길 수 있었습니다.

CDN을 도입하고 HTTP/2 프로토콜을 사용하여 해결했다고 생각했습니다.

---

## 하지만 CS는 여전했다

문제의 원인을 고민하던 중 떠오른 부분이 있었습니다. 현재 API 서버는 상해 리전에서 운영 중이고 요청한 유저의 위치는 광저우였습니다.

**당시 검색 결과에는 상해와 광저우 사이의 육로 이동 거리가 약 1,467km로 표시됐습니다.**

![2023-10-07-image1](2023-10-07-image1.png)
_상해-광저우 간 거리_

**상해와 서울 사이의 검색 결과에는 지리적 중심 간 거리가 866km로 표시됐습니다.**

![2023-10-07-image2](2023-10-07-image2.png)
_상해-서울 간 거리_

같은 국가 안에서도 지역 간 거리가 상당하다는 점을 놓치고 있었던 거죠. 다만 위의 육로 이동 거리와 지리적 중심 간 거리는 기준이 달라 그대로 비교하기 어렵고, 둘 다 실제 통신 경로 길이를 뜻하지 않습니다. 거리만으로 API 지연의 원인을 확정할 수는 없으며, 통신사 간 연결, 경로 우회, 혼잡과 패킷 손실도 영향을 줍니다.

---

## 해결 방안: 지역별 프록시 서버 + 가속화망

중국을 4등분하여 광저우, 베이징, 충칭, 상해에 프록시 서버를 세팅합니다.

![2023-10-07-image3](2023-10-07-image3.png)
_중국 4개 주요 지역 분할_

각 지역에서 오는 요청을 해당 리전의 프록시 서버로 보내고, 프록시 서버는 Tencent Cloud의 CCN(Cloud Connect Network)을 통해 상해로 요청을 전달합니다. CCN은 여러 리전의 VPC 등을 사설망으로 연결하는 서비스입니다.

![2023-10-07-image4](2023-10-07-image4.png)
_프록시 서버 + 가속화망 아키텍처_

**Before:**
```
사용자(광저우) → 공용 인터넷 → 상해 API 서버
(사용자와 API 서버 사이의 공용 인터넷 경로에서 지연)
```

**After:**
```
사용자(광저우) → 광저우 프록시 서버 → CCN 가속화망 → 상해 API 서버
(최적화된 경로, 낮은 레이턴시)
```

## 돌아보며

이번에는 이미지 전송 개선만으로 해결되지 않는 API 통신 구간을 따로 살펴보는 게 핵심이었어요. 지역별 프록시와 CCN으로 경로를 바꾸는 접근은 유효했지만, 이 결과만으로 물리적 거리가 유일한 원인이었다고 단정할 수는 없습니다.

CDN은 콘텐츠를 사용자 가까이 전달하고 캐싱하는 데 쓰이고, CCN은 사설 네트워크 사이의 연결 경로를 구성하는 데 쓰입니다. CDN도 제품과 설정에 따라 동적 요청을 가속할 수 있으므로 정적·동적 콘텐츠만으로 둘을 나누기는 어렵습니다. 중국처럼 영토가 넓은 국가에서 서비스할 때는 사용자 위치와 실제 통신 경로를 함께 고려해야 해요.
