## 카프카(Kafka)란?

Kafka는 Pub-Sub 방식으로 이벤트를 발행하고 구독할 수 있는 분산 이벤트 스트리밍 플랫폼이에요. 메시지 큐처럼 사용할 수 있지만, 소비한 이벤트도 보존 정책에 따라 로그에 남겨 다시 읽을 수 있다는 특징이 있습니다.

![2023-05-13-image7](2023-05-13-image7.png)
_Kafka 기본 아키텍처_

카프카 클러스터를 중심으로 Producer와 Consumer가 데이터를 Push하고 Pull하는 구조죠.

---

## 구성요소

**Event**: Producer와 Consumer가 데이터를 주고받는 단위입니다.

**Producer**: Kafka에 메시지를 게시하는 클라이언트 애플리케이션입니다.

**Broker**: 카프카 서버를 말합니다.

**ZooKeeper**: 분산 코디네이션 시스템이에요. ZooKeeper 방식으로 구성한 Kafka 클러스터의 메타데이터와 컨트롤러 선출 등을 관리합니다. 2023년 5월 당시에도 ZooKeeper 대신 KRaft를 사용하는 구성이 있었으므로 모든 Kafka 설치의 필수 요소는 아닙니다.

**Topic**: 메시지가 쓰이는 곳이에요. Producer는 Topic에 메시지를 게시하고 Consumer는 Topic에서 메시지를 가져와 처리합니다. 하나의 Topic은 1개 이상의 Partition으로 구성돼요.

**Partition**: Topic을 나눈 순서 있는 로그 단위입니다. Partition들을 여러 Broker에 분산하고 복제할 수 있어요. 키를 기준으로 분배하는 partitioner를 쓰고 Partition 수가 유지된다면 같은 키의 메시지는 같은 Partition으로 갑니다. Partition 수나 분배 방식이 바뀌면 달라질 수 있습니다.

**Consumer**: Topic을 구독하고 메시지를 처리하는 클라이언트 애플리케이션입니다.

## 주요 개념

### Producer와 Consumer의 분리

Kafka의 Producer와 Consumer는 완전 별개로 동작합니다. Producer는 Broker의 Topic에 메시지를 게시하기만 하면 되며 Consumer는 Broker의 특정 Topic에서 메시지를 가져와 처리하기만 하면 됩니다.

이 덕분에 Kafka는 높은 확장성을 제공해요. Producer나 Consumer를 필요에 따라 Scale In/Out 하기 용이한 구조입니다.

### Push와 Pull 모델

Kafka의 Consumer는 Pull 모델 기반으로 메시지를 처리해요. Broker가 Consumer에게 메시지를 전달하는 게 아니라, Consumer가 필요할 때 Broker에서 메시지를 가져와 처리하는 형태입니다.

Consumer가 자신의 속도에 맞춰 가져오고 여러 메시지를 모아 처리하기 쉽습니다. 다만 처리 속도가 생산 속도를 따라가지 못하면 lag가 쌓이며, fetch 대기 시간과 배치 크기에 따른 지연도 고려해야 합니다.

### Commit과 Offset

![2023-05-13-image2](2023-05-13-image2.png)
_Kafka Partition과 Offset 구조_

메시지는 Partition의 로그에 순차적으로 append 됩니다. 각 레코드에는 해당 Partition 내의 위치를 나타내는 offset이 부여됩니다.

Consumer는 현재 읽기 위치에서 다음 레코드를 가져옵니다. commit한 offset은 재시작이나 재할당 후 어디서 다시 읽을지를 정하는 저장된 위치이며, 보통 마지막으로 처리한 레코드의 offset에 1을 더한 값, 즉 다음에 읽을 위치입니다. 정상 실행 중 매번 commit한 위치에서 다시 읽는 것은 아닙니다.

> Consumer는 멱등성을 고려하여야 합니다. 같은 메시지를 여러 번 받아서 여러 번 처리하더라도 한번 처리한 것과 같은 결과를 가지도록 설계해야 합니다.
{: .prompt-warning }

### Consumer Group

Consumer Group은 같은 group ID로 하나 이상의 Topic을 구독하고 Partition을 나눠 처리하는 Consumer 모임이에요. 병렬 처리와 장애 시 재할당에 활용합니다.

![2023-05-13-image3](2023-05-13-image3.png)
_올바른 Consumer Group과 Partition 관계_

일반적인 Consumer Group에서는 각 Partition이 그룹 내 하나의 Consumer에 할당됩니다. 하나의 Consumer가 여러 Partition을 담당할 수도 있어요. Kafka가 제공하는 순서는 Partition 내부의 순서이며, 여러 Partition 전체의 순서는 보장하지 않습니다. 애플리케이션에서 병렬 처리하면 완료 순서도 별도로 고려해야 합니다.

![2023-05-13-image4](2023-05-13-image4.png)
_잘못된 Consumer Group과 Partition 관계_

같은 그룹 안에서는 하나의 Partition이 동시에 하나의 Consumer에 할당됩니다. 서로 다른 그룹은 같은 Partition을 독립적으로 읽을 수 있습니다.

**Rebalance**: Partition을 담당하던 Consumer가 죽으면, Partition과 Consumer를 재조정해서 남은 Consumer가 Partition을 나눠 처리해요.

![2023-05-13-image5](2023-05-13-image5.png)
_비효율적인 Consumer 확장_

![2023-05-13-image6](2023-05-13-image6.png)
_효율적인 Consumer 확장_

> Consumer를 늘릴 때는 구독 대상의 Partition 수를 확인하세요. 그룹의 Consumer 수가 할당 가능한 Partition 수보다 많으면 일부 Consumer는 작업을 받지 못합니다. 이미 Partition이 충분하다면 함께 늘릴 필요는 없습니다.

## 메시지 전달 방식

**At most once**: 처리 보장 관점에서 중복 처리를 피하는 대신 장애 시 메시지가 처리되지 않고 누락될 수 있어요.

**At least once**: 메시지가 최소 1번 이상 전달되는 걸 보장합니다. 동일한 메시지가 중복으로 처리될 수 있어요.

**Exactly once**: 정해진 처리 범위에서 결과가 한 번만 반영되도록 보장합니다. Kafka의 트랜잭션과 Kafka Streams 등으로 Kafka 내부의 읽기·처리·쓰기를 묶을 수 있지만, 외부 DB나 API 호출까지 자동으로 한 번만 실행되는 것은 아닙니다. 외부 시스템과 연동할 때는 추가 설계가 필요해요.

더 자세한 내용은 [Kafka 공식 문서](https://kafka.apache.org/documentation)와 작성 당시 버전에 가까운 [Kafka 3.4 설계 문서](https://kafka.apache.org/34/design/design/), [Consumer의 읽기 위치와 commit offset](https://kafka.apache.org/34/javadoc/org/apache/kafka/clients/consumer/KafkaConsumer.html)을 참고하세요.
