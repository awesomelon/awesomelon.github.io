## 🚀 들어가며

약 30년 동안 JPEG는 월드 와이드 웹의 주요 이미지 포맷이었습니다.

하지만 웹이 처음 시작할 때 사용된 포맷은 아니었습니다. 사실 최초의 대중적인 그래픽 브라우저인 NCSA Mosaic은 처음에는 인라인 JPEG 파일을 지원하지 않았고, [인라인 GIF](https://ftp.jurassic.nl/pub/irix/mosaic/Mac/FAQ/FAQ.HTML)와 지금은 [잊힌 몇 가지 다른 포맷](https://spectrum.ieee.org/carnegie-mellon-is-saving-old-software-from-oblivion)만 지원했습니다.

### JPEG와 웹의 만남

그러나 JPEG는 곧 대체한 포맷에 비해 많은 장점이 있었습니다.

| 특징 | GIF | JPEG |
|:---|:---|:---|
| 색상 지원 | 256색 | 1,670만 색 |
| 압축 방식 | 무손실 | 손실 (조절 가능) |
| 애니메이션 | ✅ 지원 | ❌ 미지원 |
| 사진 품질 | 제한적 | 우수 |

JPEG와 웹 브라우저는 처음부터 함께 등장하지는 않았지만(이미지 표준이 공식적으로 발표된 지 3년 후인 1995년에 Netscape에서 처음 등장), 둘은 자연스럽게 어울렸습니다.

> **🎯 핵심 장점**  
> JPEG 파일은 GIF보다 더 우아하게 품질이 저하되어, 이미지의 원래 형태를 더 잘 유지할 수 있었고, 덕분에 더 큰 성공을 거둘 수 있었습니다.
{: .prompt-tip }

애니메이션은 지원하지 않았지만, 모뎀이 느리게 렌더링하던 시절부터 고급 전문 사진에도 사용할 수 있을 만큼 발전했습니다.

### 진정한 차별화 요소

인터넷에서 중요한 점은 바로 이 품질 저하 방식이었습니다. 하지만 JPEG가 디지털 세계에서 엄청난 가치를 갖게 된 것은 이것만이 아니었습니다.

> **📜 표준화의 힘**  
> 중요한 점은 여러 이해관계자들이 함께 만든 **문서화된 표준**이었다는 점입니다.
{: .prompt-info }

## 📊 GIF는 사실상의 표준, JPEG는 진짜 표준

JPEG가 표준이었다는 점이 얼마나 중요할까요? 이야기를 하나 해드릴게요.

### "GIF" 발음 논쟁

2013년, GIF의 창시자인 스티브 윌하이트가 자신의 업적을 기리는 상을 받기 직전 [뉴욕타임스와의 인터뷰](https://archive.nytimes.com/bits.blogs.nytimes.com/2013/05/21/an-honor-for-the-creator-of-the-gif/?smid=tw-nytimes)에서, 그는 자신이 의도치 않게 만든 논쟁에 대해 언급했습니다.

즉, 자신이 만든 이미지 포맷(Graphics Interchange Format)의 약어를 어떻게 발음해야 하는지 아무도 몰랐던 것입니다.

> **🗣️ 윌하이트의 선언**  
> "부드러운 G, 즉 '지프(jif)'로 발음한다. 끝."
{: .prompt-info }

| 발음 | 지지자 | 근거 |
|:---|:---|:---|
| **"지프" (Jif)** | 창시자 윌하이트 | 창작자의 의도 |
| **"기프" (Gif)** | 대다수 사용자 | Graphics의 G 발음 |

저는 그 당시 인기 있던 Tumblr에 [윌하이트의 말을 인용](https://shortformblog.com/post/51026114908/steve-wilhite-gif-award)해 올렸고, 곧 수천 건의 리블로그가 달렸습니다. 대부분은 윌하이트의 발음에 동의하지 않았죠. 곧 [그의 발언은 밈이 되었습니다](https://knowyourmeme.com/memes/gif-vs-jif-pronunciation-debate/).

### 혼자 vs 위원회

이 일화는 윌하이트가 자신의 포맷을 **위원회가 아닌 혼자 개발**했다는 점을 보여줍니다.
```text
GIF 개발 과정:
1987년 → 스티브 윌하이트 (CompuServe)
       → 혼자 개발
       → 간단한 문서
       → 빠른 출시

결과: 사실상의 표준 (De facto standard)
```
{: .nolineno }

그는 1987년 CompuServe 직원으로서 이 프로젝트를 맡아 직접 만들었고, 그게 전부였습니다. 작동 방식을 설명하는 최초의 문서도 매우 간단했습니다.

38년이 지난 지금도 GIF는 여전히 사용되고 있지만, JPEG만큼 널리 퍼지지는 못했습니다.

### 표준의 차이

JPEG는 약 5년 후에 공식적으로 등장했는데, 상황이 완전히 달랐습니다.

| 구분 | GIF | JPEG |
|:---|:---|:---|
| 개발 방식 | 1인 개발 | 위원회 (수십 명) |
| 표준 유형 | 사실상 표준 | 공식 표준 |
| 문서화 | 간단한 스펙 | 600+ 페이지 |
| 이해관계자 | CompuServe | IBM, AT&T, Canon 등 |

> **🔑 결정적 차이**  
> 사실상의 표준과 진짜 표준의 차이였고, 이것이 JPEG가 널리 퍼지는 데 결정적이었습니다.
{: .prompt-tip }

## 🏗️ JPEG 포맷의 탄생

![JPEG 압축 예시 - 원본](2025-07-01-image1.jpg)
_이 기사 전체에서 이 이미지의 품질을 점점 낮춰볼 것입니다. 원래 전체 크기는 13.7메가바이트입니다._

수십 명의 이해관계자들이 참여해 만든 **JPEG(Joint Photographic Experts Group)** 는 모두의 요구를 충족하는 포맷을 만들고자 했습니다.

> **💡 명명의 명확성**  
> 위원회가 만든 만큼, 이름에 혼동이 없도록 조직의 약어를 그대로 사용했습니다.
{: .prompt-info }

### 표준화의 필요성

포맷이 세상에 공개되었을 때는 600페이지가 넘는 책으로 소개될 정도였습니다.

IBM 직원이자 JPEG 조직의 일원이었던 **윌리엄 B. 페네베이커**와 **조안 L. 미첼**이 쓴 『JPEG: 정지 영상 데이터 압축 표준』은 포토리얼리즘 이미지와 즉시성의 균형을 맞출 방법이 없던 멀티미디어 이미지의 세계를 [설명](https://www.google.com/books/edition/JPEG/AepB_PZ_WMkC?hl=en&gbpv=0)합니다.

> **📖 핵심 통찰**  
> "문제는 이미지 압축 알고리즘의 부족이 아니라, 다양한 응용 프로그램 간에 이미지를 교환할 수 있는 **표준 알고리즘의 부재**였다"
{: .prompt-warning }

이 말은 맞았습니다. 30년 넘게 JPEG는 고품질, 고해상도 사진을 다양한 운영체제에서 사용할 수 있게 했습니다.

### 협력적 개발 과정
```text
JPEG 개발 참여자:
├── IBM (개발 주도)
├── AT&T (데이터 전송)
├── Canon (프린팅, 사진)
├── 기타 통신/이미징 기업들
└── 학계 연구자들

목표: 모든 플랫폼에서 사용 가능한 표준
```
{: .nolineno }

IBM의 지원을 받아 미첼과 페네베이커는 JPEG 위원회와 함께 연구를 진행했고, 이 과정에서 JPEG 포맷의 핵심 특허를 개발했습니다.

| 참여 기업 | 관심 분야 | 기여 |
|:---|:---|:---|
| 📱 **IBM** | 종합 기술 | 핵심 알고리즘 개발 |
| 📞 **AT&T** | 데이터 전송 | 네트워크 최적화 |
| 📷 **Canon** | 프린팅, 사진 | 이미지 품질 |

1988년에 미첼과 페네베이커가 출원한 특허에서 IBM과 JPEG 위원회의 다른 멤버(AT&T, 캐논 등)는 고품질 이미지를 제한된 환경에서 쉽게 전달할 수 있도록 압축 기술을 개발했습니다.

각 회사는 각자의 필요에 따라 참여했습니다. 캐논은 프린터와 사진에, AT&T는 데이터 전송에 더 관심이 있었습니다. 이들이 남긴 표준은 지금까지도 유효합니다.

### 첫 구현: OS/2

재미있게도, JPEG 압축을 사용할 수 있는 프로그램이 처음 등장한 곳은 MacOS나 Windows가 아니라 IBM이 만든 실패한 운영체제 **OS/2**였습니다.
```text
JPEG 지원 타임라인:
1990년 → OS/2 이미지 지원 (최초)
1995년 → Netscape Navigator
1995년 → Windows 95
1990년대 후반 → 광범위한 채택
```
{: .nolineno }

1990년경, OS/2는 OS/2 이미지 지원 애플리케이션을 통해 JPEG를 지원했습니다.

## 🔬 JPEG를 강하게 압축하면 어떻게 될까

![JPEG 압축 50%](2025-07-01-image2.jpg)
_초기 품질의 50퍼센트로 낮추면, 이미지 용량이 약 2.6MB로 줄어듭니다. 이미지 품질을 절반으로 낮췄더니, 파일 크기가 원래의 5분의 1이 되었습니다._

JPEG가 PNG나 GIF와 다른 점은 데이터를 압축할 때 **어떻게 품질이 저하되는지**입니다.

### 손실 압축의 철학

JPEG의 목표는 압축이 필요하더라도 사진처럼 보이게 하는 것입니다. 즉, 원본과 비슷한 이미지를 더 적은 용량으로 보여줄 수 있습니다.

> **💬 페네베이커와 미첼의 통찰**  
> "가장 효과적인 압축은 원본 이미지를 정확히 재현하는 것이 아니라 **근사치로 만드는 것**이다."
{: .prompt-info }

| 압축 방식 | 특징 | 적합한 용도 |
|:---|:---|:---|
| **무손실** (PNG, GIF) | 원본 완벽 보존 | 텍스트, 로고, 아이콘 |
| **손실** (JPEG) | 근사치 압축 | 사진, 복잡한 이미지 |

---

### 이산 코사인 변환 (DCT)

여기서 핵심은 **이산 코사인 변환(Discrete Cosine Transform, DCT)** 이라는 압축 과정입니다.

#### DCT의 특징
```python
# DCT 압축 개념 (의사 코드)
def jpeg_compress(image, quality):
    # 1. 이미지를 8×8 블록으로 분할
    blocks = split_into_8x8_blocks(image)
    
    # 2. 각 블록에 DCT 적용
    for block in blocks:
        dct_block = apply_dct(block)
        
        # 3. 양자화 (품질에 따라 조절)
        quantized = quantize(dct_block, quality)
        
        # 4. 엔트로피 인코딩
        encoded = entropy_encode(quantized)
    
    return encoded_image
```
{: file='jpeg_compression.py' }

| DCT 특성 | 설명 |
|:---|:---|
| 📉 **손실 압축** | 데이터 일부 제거 |
| 🎚️ **조절 가능** | 품질-용량 트레이드오프 |
| 🔄 **가역적** | 근사치로 복원 가능 |
| 📊 **주파수 변환** | 공간 → 주파수 도메인 |

DCT는 손실 압축 방식으로, 디지털 오디오와 신호 처리 등 다양한 분야에서 사용됩니다. 데이터를 줄이면서도 원본의 핵심을 근사치로 유지합니다.

> **🚰 수도꼭지 비유**  
> 이 알고리즘은 1970년대에 개발되었으며, 데이터를 마치 수도꼭지처럼 조절할 수 있게 해줍니다. 더 많은 데이터를 원하면 더 많이, 적게 원하면 적게 흘러나오게 할 수 있습니다.
{: .prompt-tip }

### JPEG 압축 모드

JPEG 표준은 하나의 압축 방식만 제공하는 것이 아니라, 다양한 압축 기술의 **"도구 상자"** 를 제공합니다.

도구 상자는 네 가지 모드가 있습니다:

#### 1. 순차 DCT (Sequential DCT)

압축된 이미지를 위에서 아래로 순서대로 표시(블라인드처럼)
```text
로딩 순서:
████████████████████ (상단)
████████████████████
████████████████████
░░░░░░░░░░░░░░░░░░░░ (하단, 아직 로드 안 됨)
```
{: .nolineno }

#### 2. 점진적 DCT (Progressive DCT)

전체 이미지를 낮은 해상도로 먼저 보여주고, 점차 디테일을 추가
```text
로딩 단계:
1단계: ▓▓▓▓▓▓▓▓ (흐릿함)
2단계: ████████ (조금 선명)
3단계: ████████ (더 선명)
4단계: ████████ (완전)
```
{: .nolineno }

#### 3. 순차 무손실 (Sequential Lossless)

블라인드 방식이지만 압축하지 않음

#### 4. 계층적 모드 (Hierarchical Mode)

앞의 세 가지를 조합(예: 점진적으로 시작해 무손실로 마무리)

| 모드 | 장점 | 단점 | 주 사용 시기 |
|:---|:---|:---|:---|
| **순차 DCT** | 빠른 디코딩 | 순차적 표시 | 현대 웹 |
| **점진적 DCT** | UX 개선 | 느린 디코딩 | 느린 연결 |
| **무손실** | 품질 완벽 | 큰 파일 크기 | 아카이브 |
| **계층적** | 유연성 | 복잡도 높음 | 특수 용도 |

> **⏰ 역사적 맥락**  
> JPEG가 만들어질 당시에는 모뎀이 흔했기 때문에, 이미지를 천천히 로딩하는 점진적 DCT가 인터넷에 가장 적합했습니다. 시간이 지나면서 컴퓨터 성능이 좋아져 순차 DCT가 더 많이 쓰이게 되었습니다.
{: .prompt-info }

### 압축 아티팩트

![JPEG 극한 압축](2025-07-01-image3.jpg)
_같은 숲 사진을 품질 5퍼센트로 저장하면, 이제 약 419킬로바이트로 줄어듭니다._

이미지를 DCT로 압축하면 특정 패턴의 아티팩트가 나타납니다:

| 이미지 유형 | 압축 효과 | 품질 |
|:---|:---|:---|
| 복잡한 디테일 (머리카락, 나뭇잎) | 변화 덜 눈에 띔 | ✅ 양호 |

> 그래서 소셜 미디어 게시물을 스크린샷하면 노이즈가 생기는 것입니다.
{: .prompt-warning }

### 다른 포맷과의 비교

PNG 같은 다른 포맷은 텍스트에 더 적합합니다.
```text
압축 알고리즘 비교:

JPEG: DCT (손실)
└── 사진, 복잡한 이미지

PNG: DEFLATE (무손실)
└── 텍스트, 로고, 스크린샷

GIF: LZW (무손실)
└── 단순한 그래픽, 애니메이션
```
{: .nolineno }

PNG의 압축 방식(DEFLATE)은 ZIP 포맷을 만든 **필 카츠(Phil Katz)** 가 개발했으며, 라이선스가 필요 없는 압축 방식이기 때문에 사용되었습니다.

> **🔧 도구 선택의 중요성**  
> JPEG는 이미지 제작 도구 중 하나일 뿐입니다. 오래되고 성숙한 포맷이지만, 인터넷에서 사진을 공유할 때 여전히 최고의 선택지 중 하나입니다. 하지만 모든 상황에 적합한 도구는 아닙니다.
{: .prompt-tip }

---

## ⚖️ 포전트 네트웍스(Forgent Networks)는 JPEG의 핵심 알고리즘을 소유했다고 주장했다

JPEG가 90년대에 인기를 끈 이유는 포맷의 품질뿐만 아니라 **특허** 때문이기도 했습니다.

### GIF 특허 논란

1994년, **유니시스(Unisys)** 는 자신들이 소유한 특허를 사용한 GIF 파일 사용자들에게 요금을 청구하려 했습니다.
```text
GIF 특허 사태:
1994 → Unisys, LZW 압축 특허 주장
     → GIF 사용자에게 로열티 요구
     → 개발자 커뮤니티 반발

결과:
✅ JPEG 인기 급상승 (무료)
✅ PNG 포맷 탄생 (특허 없음)
```
{: .nolineno }

이로 인해 무료로 사용할 수 있는 JPEG가 더 인기를 끌었습니다. (이 일로 특허가 없는 PNG 포맷도 탄생했습니다.)

---

### JPEG 특허 공격

JPEG도 특허 문제에서 자유로울 수는 없었습니다.

#### 컴프레션 랩스 특허

포맷이 등장하기 몇 년 전, **컴프레션 랩스(Compression Labs)** 직원 두 명이 모션 그래픽 압축에 관한 특허를 출원했습니다.

| 시기 | 사건 |
|:---|:---|
| 1980년대 중반 | Compression Labs, 모션 압축 특허 출원 |
| 1992년 | JPEG 표준 공식 발표 |
| 1997년 | Forgent Networks, Compression Labs 인수 |
| 2000년대 초 | Forgent, JPEG 특허 주장 및 소송 시작 |
| 2007년 | 특허 만료 |

나중에 이 특허가 JPEG 압축과 유사하다는 사실이 알려졌을 때는 이미 JPEG가 널리 퍼진 뒤였습니다.

#### 포전트의 공격적 소송

1997년, **포전트 네트웍스**가 컴프레션 랩스를 인수했습니다. 이후 이 특허를 발견하고 소송을 제기하기 시작했습니다.

> **🎰 CEO의 고백**  
> 포전트 CEO 제이 피터슨은 2005년 CNET과의 인터뷰에서 "이 특허는 어떤 면에서 복권과 같다. 5년 전에 '네가 JPEG 특허를 갖고 있다'고 했다면 믿지 않았을 것"이라고 말했습니다.
{: .prompt-info }

#### 소송 성과

| 대상 | 결과 | 금액 |
|:---|:---|---:|
| 디지털 카메라 제조사 | 라이선스 계약 | $100M+ |
| PC 업계 | 합의 | $8M |

포전트의 JPEG 압축 알고리즘 소유 주장은 미약했지만, 결국 유니시스보다 더 많은 성공을 거두었습니다.
```text
포전트의 전략:
1. 특허 발견 및 주장
   ↓
2. 카메라 제조사 공략
   → 1억 달러 이상 확보
   ↓
3. PC 업계 압박
   → 800만 달러 합의
   ↓
4. 법정 및 여론에서 불리해짐
   ↓
5. 2007년 특허 만료
```
{: .nolineno }

공격적인 특허 소송이 이어지자, 법원과 여론 모두에서 점점 불리해졌습니다. 결국 2007년 특허가 만료되었고, 포전트는 소프트웨어 회사(**Asure Software**)로 전환했습니다.

## 🔄 JPEG가 사라지지 않는 이유

JPEG 파일 포맷은 오랫동안 우리 곁에 있었습니다. 쉽게 대체되지 않았죠.

### 후속 포맷들의 도전

| 포맷 | 출시 | 장점 | 채택 현황 |
|:---|:---:|:---|:---|
| **JPEG 2000** | 2000년 | 무손실 옵션, 더 나은 압축 | ⚠️ 제한적 |
| **WebP** | 2010년 | 작은 파일 크기 | 🟡 개발자 중심 |
| **AVIF** | 2019년 | 우수한 압축률 | 🟢 증가 중 |
| **HEIC** | 2017년 | 효율적 압축 | 🍎 Apple 생태계 |

#### JPEG 2000의 실패

JPEG 2000 같은 포맷이 더 나은 성능과 무손실 옵션을 제공하며 대체를 시도했지만, 일반 사용자에게는 인기가 없었습니다.
```text
JPEG 2000 실패 요인:
❌ 복잡한 구현
❌ 브라우저 지원 부족
❌ 기존 도구와 호환성 문제
❌ 성능 개선이 체감되지 않음
```
{: .nolineno }

#### WebP의 논란

구글이 지원하는 **WebP**는 웹사이트 개발자들 사이에서 인기가 있지만, 사용자들 사이에서는 논란이 있습니다.

| WebP 장점 | WebP 단점 |
|:---|:---|
| 우수한 압축률 | 제한적인 도구 지원 |
| 알파 채널 지원 | 다운로드 시 호환성 문제 |
| 애니메이션 지원 | 느린 인코딩/디코딩 |

#### 새로운 경쟁자들

AVIF와 HEIC 같은 포맷은 JPEG와 JPEG 2000을 능가하는 성능을 보이기도 합니다.

---

### 네트워크 효과

그럼에도 불구하고 JPEG는 여전히 살아남고 있습니다.
```text
JPEG의 네트워크 효과:

30년의 역사
    ↓
모든 디바이스 지원
    ↓
모든 소프트웨어 호환
    ↓
사용자 익숙함
    ↓
대체 비용 증가
    ↓
지배력 유지
```
{: .nolineno }

| 레거시 포맷 | 특징 | 생존 이유 |
|:---|:---|:---|
| 📷 **JPEG** | 이미지 압축 | 보편적 지원 |
| 🎵 **MP3** | 오디오 압축 | 익숙함 |
| 📦 **ZIP** | 파일 압축 | 표준화 |

> **🔒 교체 저항성**  
> MP3나 ZIP 파일처럼 너무 널리 퍼져서 사라지기 힘든 포맷입니다. 더 효율적인 포맷이 있지만, 30년의 역사를 가진 포맷을 대체하는 것은 쉽지 않습니다.
{: .prompt-info }

## 🎓 결론

JPEG를 완전히 없애는 것은 말처럼 쉽지 않습니다.

### JPEG의 지속 가능성 요인

| 요인 | 설명 |
|:---|:---|
| 🌐 **보편적 지원** | 모든 플랫폼, 모든 디바이스 |
| 📜 **개방형 표준** | 로열티 없음, 자유로운 구현 |
| 🔧 **성숙한 도구** | 수십 년간 최적화된 라이브러리 |
| 👥 **사용자 익숙함** | 학습 비용 없음 |
| ⚖️ **균형잡힌 성능** | 품질과 용량의 적절한 타협 |

더 새롭고 효율적인 포맷들이 등장하고 있지만, JPEG의 자리를 완전히 대체하기까지는 아직 시간이 필요할 것입니다.

> **💭 현실적 전망**  
> 대부분의 사람들은 그냥 계속 사용할 것입니다.
{: .prompt-tip }

JPEG의 성공은 기술적 우수성만이 아니라, **표준화**, **개방성**, **적시성**이 결합된 결과였습니다. 이는 기술 표준이 어떻게 생태계를 형성하고 지배할 수 있는지 보여주는 훌륭한 사례입니다.
