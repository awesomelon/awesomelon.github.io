브라우저 주소창에 `google.com`을 입력하면 어떤 일이 벌어질까요? URL 입력부터 웹 페이지가 화면에 뜨기까지의 흐름을 정리해봤습니다.

---

## 1. DNS 캐시 확인

DNS(Domain Name System)는 도메인 이름을 IP 주소 등 여러 종류의 레코드에 연결하는 분산 시스템입니다. URL 전체가 아니라 `google.com` 같은 호스트 이름을 조회합니다. 하나의 이름이 여러 IP 주소에 연결되거나 여러 이름이 같은 IP 주소를 사용할 수 있어요.

google.com의 IP 주소를 알아보려면 터미널에서 `nslookup google.com`을 입력합니다.

![2022-11-12-image1](2022-11-12-image1.png)
_nslookup 명령어 실행 결과_

DNS 덕분에 사람은 숫자로 된 IP 주소 대신 네이버, 다음, 구글처럼 익숙한 이름을 사용할 수 있습니다. 다만 가상 호스팅과 HTTPS 인증서 때문에 IP 주소만 입력해서는 원하는 사이트에 접속하지 못할 수도 있어요.

도메인 이름을 조회할 때는 여러 계층의 DNS 캐시를 활용할 수 있습니다. 다만 아래 순서가 모든 환경에서 고정된 것은 아닙니다:

1. **브라우저 캐시**: 브라우저는 일정 기간 동안의 DNS 기록을 저장
2. **OS 캐시**: OS의 이름 해석 기능을 사용하는 경우 참조
3. **Router 캐시**: 공유기가 DNS 프록시와 캐시 기능을 제공할 때 사용
4. **재귀 리졸버 캐시**: ISP 또는 사용자가 지정한 공용 DNS 서버 등에서 참조

브라우저가 DNS over HTTPS를 사용하면 OS나 공유기의 DNS 처리 경로를 거치지 않을 수도 있습니다.

이런 캐시 덕분에 네트워크 트래픽이 줄어들고 데이터 전송 시간도 단축됩니다.

---

## 2. DNS Query 실행

필요한 레코드가 캐시에 없으면, 설정된 재귀 리졸버가 `google.com`의 IP 주소를 찾기 위해 DNS 서버들에 질의합니다.

클라이언트는 보통 리졸버에 재귀 질의를 보내 최종 답을 요청합니다. 리졸버는 루트, 최상위 도메인, 권한 있는 DNS 서버를 대상으로 반복 질의를 수행합니다. 이미 캐시된 정보가 있다면 일부 단계는 생략합니다.

![2022-11-12-image2](2022-11-12-image2.png)
_도메인 이름의 계층 구조_

google.com DNS 조회 과정:
1. DNS recursor가 root name server에 연락
2. root name server는 .com 도메인의 name server 정보를 반환
3. .com name server는 google.com의 권한 있는 name server 정보를 반환
4. google.com name server는 DNS 기록에서 google.com에 매칭되는 IP 주소를 찾고 DNS recursor로 전송

## 3. TCP Connection 수립

브라우저가 IP 주소를 받으면 서버와 연결을 수립합니다. 여기서는 새 연결을 만드는 HTTP/1.1 또는 HTTP/2의 TCP 흐름을 설명합니다. 기존 연결을 재사용하면 이 단계를 생략할 수 있고, HTTP/3는 UDP 기반 QUIC을 사용합니다.

TCP로 통신하려면 먼저 클라이언트와 서버 사이에 연결을 수립해야 합니다. 이는 TCP/IP three-way handshake 프로세스를 통해 이뤄집니다.

1. **SYN**: 클라이언트가 서버에 connection을 열어달라고 요청
2. **SYN/ACK**: 해당 포트에서 연결을 수락한 서버가 SYN을 확인하고 자신의 SYN을 보냄
3. **ACK**: 클라이언트가 SYN/ACK를 받으면 서버에게 확인 패킷 전송

이 과정이 끝나면 TCP connection이 완성됩니다. HTTPS에서는 이어서 TLS 핸드셰이크로 서버 인증서 등을 확인하고 암호화 통신을 준비합니다.

---

## 4. HTTP 요청 전송

연결이 준비되면 브라우저는 GET 요청으로 웹 페이지를 요구합니다. 폼 제출 등에는 POST 요청을 사용할 수도 있지만, POST 자체가 데이터를 암호화하는 것은 아닙니다. 전송 내용의 보호는 HTTPS가 담당합니다.

요청에는 이런 정보가 포함됩니다.
- User-Agent: Browser identification
- Accept: 클라이언트가 받아들일 응답의 미디어 타입
- Connection: HTTP/1.1에서 연결 관련 옵션 지정. HTTP/2와 HTTP/3에서는 사용하지 않음
- Cookie: 저장된 쿠키 정보

---

## 5. 서버의 요청 처리

서버에서는 Nginx, Apache, IIS 같은 웹 서버나 Node.js 등으로 작성한 서버 애플리케이션이 요청을 처리합니다.

1. 브라우저로부터 요청을 받음
2. 요청을 Python, Go, JS, JAVA 등으로 작성된 프로그램에 전달
3. 요청의 헤더, 쿠키를 읽어서 요청 내용 파악
4. 필요시 서버에 정보 업데이트
5. 특정 포맷으로 응답 작성 (JSON, XML, HTML 등)

---

## 6. HTTP Response 반환

서버의 응답에는 상태 코드, 헤더, 필요한 경우 본문이 포함됩니다. 헤더에는 Content-Type, Content-Encoding, Cache-Control, Set-Cookie 등이 올 수 있고, 본문에는 요청한 HTML 등이 담깁니다.

## 7. HTML 렌더링

브라우저는 HTML content를 단계적으로 보여줍니다.

1. HTML을 파싱해 DOM 구성
2. CSS, JavaScript, 이미지 등 필요한 리소스 요청
3. CSS를 파싱하고 DOM과 함께 렌더링에 필요한 구조 구성
4. 레이아웃 계산, 페인트와 합성으로 화면 표시
5. 추가 리소스 로딩이나 JavaScript 실행에 따라 화면 갱신

이 단계들은 일부 겹쳐 진행되며, 스크립트나 스타일시트가 파싱 또는 렌더링을 지연시킬 수도 있습니다.

리소스는 캐시 정책에 따라 저장하고 재사용할 수 있습니다. 만료 여부와 응답 헤더에 따라 서버에 재검증하거나 다시 내려받기도 합니다.
