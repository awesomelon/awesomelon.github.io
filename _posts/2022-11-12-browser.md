## 🚀 들어가며

브라우저 주소창에 `google.com`을 입력하면 어떤 일이 벌어질까요?
이 글에서는 URL 입력부터 웹 페이지가 화면에 나타나기까지의 전체 과정을 **7단계**로 나누어 살펴보겠습니다.

## 1️⃣ DNS 캐시 확인

### DNS란?

> **DNS(Domain Name System)**는 URL들의 이름과 IP 주소를 저장하고 있는 데이터베이스입니다.
{: .prompt-tip }

인터넷에 있는 모든 URL들에는 **고유의 IP 주소**가 지정되어 있습니다. 이 IP 주소를 통해서 해당 웹 사이트를 호스팅하고 있는 서버 컴퓨터에 접근할 수 있습니다.

### IP 주소 확인 방법

[google.com](https://google.com)의 IP 주소를 알아보려면 아래 커맨드를 터미널에 입력합니다:

```bash
nslookup google.com
```

현재 제가 있는 지역에서 해당 명령어를 실행했을 때 `142.251.42.206`이 반환되었고, 이 IP 주소를 브라우저에서 검색했을 때 google.com과 동일한 결과가 나왔습니다.

![2022-11-12-image1](2022-11-12-image1.png)
_nslookup 명령어 실행 결과_

> **non-authoritative answer**란?
> name 서버가 도메인에서 만든 원본 소스 파일을 갖고 있지 않다는 뜻입니다.
> 이 서버에는 다른 DNS들에서 얻어진 도메인의 파일을 **캐싱 형태**로 갖고 있는 것입니다.
{: .prompt-warning }

### DNS의 목적

DNS의 가장 큰 목적은 **사람들에게 편리함을 주기 위함**입니다.

- 숫자로 된 IP 주소를 작성해도 원하는 웹 사이트에 접속할 수 있습니다
- 하지만 매번 랜덤해 보이는 숫자들을 검색하는 것은 매우 복잡한 일입니다
- 사람은 **네이버, 다음, 구글**처럼 이름을 외우는 것에 더 친숙하기 때문입니다

### DNS 기록 확인 순서

웹 사이트 이름을 브라우저에 검색하면 브라우저는 DNS 기록을 **4가지 캐시**에서 순차적으로 확인합니다:

| 순서 | 캐시 종류 | 설명 |
|:---:|:---|:---|
| 1 | **브라우저 캐시** | 브라우저는 일정 기간 동안의 DNS 기록들을 저장하고 있습니다. DNS Query는 이곳에서 가장 먼저 실행됩니다. |
| 2 | **OS 캐시** | 브라우저 캐시에서 IP 주소가 발견되지 않으면, systemcall을 통해 OS가 저장하고 있는 DNS 기록 캐시에 접근합니다. |
| 3 | **Router 캐시** | 컴퓨터에서 DNS 기록을 찾지 못하면 DNS 기록을 캐싱하고 있는 router와 통신합니다. |
| 4 | **ISP 캐시** | ISP는 DNS 서버를 구축하고 있고, 브라우저는 마지막으로 여기서 DNS 기록을 찾습니다. |

> **왜 이렇게 많은 곳에서 캐시를 저장할까요?**
> 개인 정보 측면에서는 불편할 수 있지만, 캐시는 **네트워크 트래픽을 조절**하고 **데이터 전송 시간을 줄이기 위해** 매우 중요합니다.
{: .prompt-info }

## 2️⃣ DNS Query 실행

### Recursive Search

요청한 URL이 캐시에 없으면, ISP의 DNS 서버가 google.com을 호스팅하고 있는 서버의 IP 주소를 찾기 위해 **DNS query**를 날립니다.

DNS Query의 목적은 여러 다른 DNS 서버들을 검색해서 해당 사이트의 IP 주소를 찾는 것입니다. 이러한 검색을 **`recursive search`**라고 부릅니다.

> IP 주소를 찾을 때까지 DNS 서버에서 다른 DNS 서버를 오가면서 반복적으로 검색을 하거나, 못 찾아서 에러가 발생할 때까지 검색을 진행합니다.
{: .prompt-tip }

### 주요 용어 정리

DNS recursor
: ISP의 DNS 서버로, 인터넷을 통해 다른 DNS 서버들에게 물어 물어 도메인 이름의 올바른 IP 주소를 찾는 책임을 가지고 있습니다.

Name server
: 웹 사이트 도메인 이름의 구조에 기반해서 검색을 수행하는 DNS 서버입니다.

### 도메인 이름 구조

![2022-11-12-image2](2022-11-12-image2.png)
_도메인 이름의 계층 구조_

우리가 마주하는 웹 사이트 URL들은 다음과 같은 구조를 가지고 있습니다:

- **Third-level domain** (예: www)
- **Second-level domain** (예: google)
- **Top-level domain** (예: .com)

각 레벨별로 자신들만의 name server가 있고 여기서 DNS lookup 프로세스 중에 쿼리가 진행됩니다.

### google.com DNS 조회 과정

1. `DNS recursor`가 `root name server`에 연락을 합니다.
2. `root name server`는 `.com` 도메인 `name server`로 리다이렉트 합니다.
3. `.com name server`는 `google.com name server`로 리다이렉트 합니다.
4. `google.com name server`는 DNS 기록에서 google.com에 매칭 되는 IP 주소를 찾고 `DNS recursor`로 보내게 됩니다.

### 패킷 전송

이 모든 요청들은 작은 **데이터 패킷**들을 통해서 보내집니다:

- 패킷 안에는 보내는 요청의 내용과 DNS recursor의 IP 주소가 포함
- 패킷들은 원하는 DNS 기록을 가진 DNS 서버에 도달할 때까지 클라이언트와 서버를 여러 번 오갑니다
- **Routing table**을 통해 가장 빠른 경로를 확인
- 패킷이 도중에 loss 되면 `request fail error` 발생

## 3️⃣ TCP Connection 수립

브라우저가 올바른 IP 주소를 받게 되면 서버와 **connection**을 빌드하게 됩니다.

> 웹 사이트의 HTTP 요청에는 일반적으로 **TCP**를 사용합니다.
{: .prompt-info }

### TCP/IP Three-way Handshake

클라이언트와 서버 간 데이터 패킷들이 오가려면 **TCP connection**이 되어야 합니다. 이는 **`TCP/IP three-way handshake`** 프로세스를 통해 이뤄집니다.

```
┌─────────┐                              ┌─────────┐
│ Client  │                              │ Server  │
└────┬────┘                              └────┬────┘
     │                                        │
     │  ───────── 1. SYN ─────────────────▶  │
     │                                        │
     │  ◀──────── 2. SYN/ACK ─────────────   │
     │                                        │
     │  ───────── 3. ACK ─────────────────▶  │
     │                                        │
     ▼                                        ▼
   Connection Established! ✅
```

| 단계 | 패킷 | 설명 |
|:---:|:---:|:---|
| 1 | **SYN** | 클라이언트가 서버에 connection을 열어달라고 요청 |
| 2 | **SYN/ACK** | 서버가 새로운 connection을 시작할 수 있는 포트가 있다면 응답 |
| 3 | **ACK** | 클라이언트가 SYN/ACK를 받으면 서버에게 확인 패킷 전송 |

> 이 과정이 끝나면 **TCP connection이 완성**됩니다! 🎉
{: .prompt-tip }

## 4️⃣ HTTP 요청 전송

TCP로 연결이 되었다면 이제 **데이터를 전송**할 차례입니다.

클라이언트의 브라우저는 **GET 요청**을 통해 서버에게 google.com 웹 페이지를 요구합니다.
비밀 자료를 포함하거나, form을 제출하는 상황에서는 **POST 요청**을 사용할 수도 있습니다.

### 요청에 포함되는 정보

| Header | 설명 |
|:---|:---|
| `User-Agent` | Browser identification |
| `Accept` | 받아들일 요청의 종류 |
| `Connection` | 추가적인 요청을 위해 TCP connection 유지 요청 |
| `Cookie` | 저장된 쿠키 정보 |

---

## 5️⃣ 서버의 요청 처리

서버는 웹 서버(NginX, NodeJs, Apache, IIS 등)를 가지고 있습니다.

### 처리 과정

1. **요청 수신**: 브라우저로부터 요청을 받음
2. **Request Handler 전달**: 요청을 Python, Go, JS, JAVA 등으로 작성된 프로그램에 전달
3. **요청 분석**: 요청의 헤더, 쿠키를 읽어서 요청 내용 파악
4. **서버 업데이트**: 필요시 서버에 정보 업데이트
5. **Response 생성**: 특정 포맷으로 응답 작성 (JSON, XML, HTML 등)

---

## 6️⃣ HTTP Response 반환

서버의 response에는 다음 정보들이 포함됩니다:

- ✅ 요청한 웹 페이지
- ✅ Status code
- ✅ Compress type (`Content-Encoding`)
- ✅ `Cache-Control`
- ✅ 설정할 쿠키 (있다면)
- ✅ 개인 정보

## 7️⃣ HTML 렌더링

브라우저는 HTML content를 **단계적으로** 보여줍니다.

### 렌더링 과정

1. HTML 스켈레톤 렌더링
2. HTML tag 체크
3. 추가 필요한 웹 페이지 요소들 GET 요청
   (CSS, JavaScript, 이미지 등)
4. 정적 파일 브라우저 캐싱
5. 🎉 google.com 완성!

> 정적 파일들은 브라우저에 의해 **캐싱**되어 나중에 해당 페이지를 방문할 때 다시 서버로부터 불러오지 않아도 됩니다.
