## 🚀 들어가며

이번에 회사 서비스에 [Redis](https://redis.io/)란 것을 도입하게 되었습니다.

> **데이터를 메모리에서 처리함으로써 더 빠른 연산을 도모하고 DB의 부하를 덜기 위한 것(캐싱)**이었습니다.

Redis 문서가 잘 되어 있어서 서비스에 도입하는 데까진 문제가 없었습니다.

하지만 Redis를 도입하면서도 스스로에게 캐시가 뭐냐고 물었을 때 누구나 말할 수 있는 **간단한 답밖에 하지 못한다는 것**을 깨달았습니다.

그래서 이번 기회에 캐시란 무엇인가 정리해보고자 합니다.

---

## 💡 캐시(Cache)란?

> 컴퓨터 과학에서 **데이터나 값을 미리 복사해 놓은 임시 장소**를 일컫습니다.  
> 원본 데이터에 접근하는데 걸리는 시간이 캐시의 접근 시간보다 오래 걸리는 경우나 값을 다시 계산하는데 걸리는 시간을 단축시키고 싶은 경우 사용합니다.
{: .prompt-tip }

예를 들자면, 다이소 본점에 가서 물티슈 하나 사는 것보다 **집 앞에 있는 다이소**에 가는 게 더 빠르게 사 올 수 있습니다.

---

### 🎯 캐시에는 어떤 정보를 담아야 할까?

캐시에 담을 정보를 생각할 때 많이 고려하는 법칙이 있습니다. 바로 [파레토의 법칙](https://ko.wikipedia.org/wiki/%ED%8C%8C%EB%A0%88%ED%86%A0_%EB%B2%95%EC%B9%99)입니다.

> **파레토의 법칙**이란 전체 결과의 **80%가 전체 원인의 20%**에서 일어나는 현상을 가리킵니다.
{: .prompt-info }

약간 말이 아리송한데 해석하자면 이런 뜻입니다:

| 분야 | 설명 |
|:---|:---|
| 👕 **패션** | 즐겨 입는 옷의 80%는 옷장에 걸린 옷의 20%에 불과하다 |
| 🚗 **교통** | 20%의 운전자가 전체 교통 위반의 80% 정도를 차지한다 |
| 💼 **업무** | 성과의 80%는 근무시간 중 집중력을 발휘한 20%의 시간에 이뤄진다 |
| 🧠 **문제 해결** | 우수한 20%의 인재가 80%의 문제를 해결한다 |
| 🏆 **스포츠** | 운동선수 중 20%가 전체 상금 80%를 싹쓸이한다 |
| 🌐 **인터넷** | 인터넷 유저의 20%가 80%의 양질의 정보를 생산한다 |

이것을 웹 서비스 분야에 적용하자면 **전체 요청 중 80%는 나머지 20%가 차지한다.**

쉽게 말해 **전체 요청 중 80%는 같은 요청**이라는 이야기입니다.

> 💡 그래서 캐시에 담을 정보는 **본인 서비스에서 어떤 요청이 가장 많은지 파악**한 다음 적용해야 합니다.
{: .prompt-tip }

---

### 📍 지역성 (Locality)

캐시에 담을 정보를 파악하는 데 사용하는 개념입니다. 이 개념을 토대로 캐시에 담을 정보를 선별합니다.

#### ⏰ 시간 지역성 (Temporal Locality)

> 한번 요청받았던 정보는 **가까운 시일 내에 또 요청받을 수 있다**는 개념입니다.

같은 쿼리로 여러 차례 요청을 받았다면 그 요청만 캐시에 저장해도 성능의 향상을 꾀할 수 있습니다.

#### 📦 공간 지역성 (Spatial Locality)

> 특정 데이터와 **가까운 주소가 순서대로 접근**되었을 경우를 공간 지역성이라고 합니다.

CPU 캐시나 디스크 캐시의 경우 한 메모리 주소에 접근할 때 그 주소뿐 아니라 **해당 블록을 전부 캐시에 가져오게** 됩니다.

이때 메모리 주소를 오름차순이나 내림차순으로 접근한다면, 캐시에 이미 저장된 같은 블록의 데이터를 접근하게 되므로 **캐시의 효율성이 크게 향상**됩니다.

**예시 코드:**

```javascript
// 페이지네이션 요청 예시
{ skip: 0,  limit: 10 }
{ skip: 10, limit: 10 }
{ skip: 20, limit: 10 }
{ skip: 30, limit: 10 }
```
{: .nolineno }

예를 들어 `skip: 30, limit: 10`이 캐시 할 데이터였다고 하더라도 특정 데이터에 접근하려고 순서대로 요청이 온다면 그 요청들을 캐시 하는 것이 성능 향상을 꾀할 수 있습니다.

---

### 🤔 여기서 드는 의문

캐시가 효율이 좋다면 이렇게 번거롭게 데이터를 선별하지 말고 **다 저장하면 되지 않을까?**

물론 저장해도 됩니다... **💰 돈이 많다면!!!**

메모리를 계속 추가해가며 서비스를 유지할 수도 있을 것입니다.

하지만 우린 일개 회사에 소속된 개발자이기 때문에 **효율을 따져보고 최상의 결과를 내야 합니다.**

> ### **"CACHE IS CASH"** 💵

## 📚 캐싱 전략

캐싱 전략이란 캐시를 위한 방법을 의미합니다. **디자인 패턴** 같은 개념이라고 생각하면 편합니다.

---

### 1️⃣ Cache Aside (Lazy Loading / Look Aside)

**`Cache Aside`** 전략이라고 하기도 하고 **`Lazy Loading`** 전략이라고 하기도 하고 **`Look Aside`** 전략이라고 하기도 합니다. 많은 이름이 있는 만큼 **보편적으로 쓰이는 전략**입니다.

![2022-10-15-2022-10-15-image1](2022-10-15-image1.jpeg)
_Cache Aside 전략 흐름도_

캐시는 DB와 직접 연결되지 않고, **애플리케이션**(예: 웹 API 서버)이 주체가 됩니다.

애플리케이션이 요청을 받으면, 데이터가 캐시 서버에 있는지 확인을 하며 그 결과에 따라 다음 행동이 결정됩니다:

| 상태 | 동작 |
|:---:|:---|
| ✅ **Cache Hit** | 캐시에 데이터가 있으면 그것을 바로 반환 |
| ❌ **Cache Miss** | 캐시에 데이터가 없으면 DB에서 데이터를 확인하고, 캐시에 저장 후 반환 |

#### ✅ 장점

1. **요청받은 데이터만 캐시**에 저장하므로 불필요한 데이터를 담지 않음
2. 캐시 미스가 일어나도 **치명적이지 않음** (DB 확인 로직이 있기 때문)

#### ❌ 단점

**1. 동시성 문제**

캐시에 데이터가 있는 채로 DB의 데이터가 UPDATE 되었다면 **캐시와 DB의 데이터가 다를 수 있음**

**2. 캐시 미스 시 지연 발생**

- 캐시 미스 발생 → DB에 확인 요청
- DB에서 받은 데이터 → 캐시에 쓰기 요청

> 즉, **처음 받는 요청은 지연**이 있습니다.
{: .prompt-warning }

#### 🔧 해결책

**1. 동시성 문제 해결**

> 캐시 데이터에 **만료 기간(TTL: Time to Live)**을 설정합니다.

일정 시간 경과 시 캐시에 있는 데이터를 지워줌으로써 DB와의 동시성을 유지할 수 있습니다.
캐시 미스가 일어났을 시 DB에서 데이터를 새로 가져오는 것을 노리는 것입니다.

**2. 캐시 미스 지연 해결**

> **미리 많이 요청될 것 같은 데이터를 캐시**해두는 것입니다.

예를 들어 메인 페이지에서 쓰는 데이터들이나 상품 페이지 같은 것들입니다.
스케줄 작업을 통하여 메인에서 쓰는 데이터나 상품 페이지 (전체를 다 하는 건 좀 무리니 1~5페이지 정도..?)를 캐시 해 둔다면 효율적일 것입니다.

---

### 2️⃣ Write Through

애플리케이션이 직접 바라보는 것은 DB가 아니라 **캐시**가 됩니다.

> 캐시가 **주 DB 역할**을 수행하고, DB와 동기화하는 몫은 캐시에 위임됩니다.

데이터가 **캐시와 DB에 모두 반영**되었을 때 정상적으로 성공했다고 간주합니다.
그리고 요청이 오면 애플리케이션은 캐시에서 값을 읽어서 바로 반환합니다.

![2022-10-15-image2](2022-10-15-image2.jpeg)
_Write Through 전략 흐름도_

#### ✅ 장점

Cache Aside 전략에서 있던 **동시성 문제를 해결**할 수 있습니다.
데이터가 저장되거나 변경되었을 시 캐시 데이터도 갱신해주기 때문에 동시성을 유지할 수 있습니다.

#### ❌ 단점

1. 불필요한 데이터까지도 캐시에 담길 수 있어서 **메모리 낭비** 가능
2. 값을 쓸 때마다 캐시에도 데이터 갱신을 해야 하기 때문에 **쓰기 작업이 많은 서비스라면 성능 저하** 가능
3. 캐시 미스 발생 시 캐시에 데이터를 넣어주기가 **애매함**

---

### 3️⃣ Read Through

애플리케이션이 바라보는 것은 DB가 아니라 **캐시**입니다. 따라서 DB 동기화하는 몫은 캐시에 위임됩니다.

> 최초 데이터 로딩은 **미스가 발생**하며, 그때 데이터가 로딩됩니다. 그 후에는 캐시가 처리합니다.

![2022-10-15-image3](2022-10-15-image3.jpeg)
_Read Through 전략 흐름도_

| 비교 | Cache Aside | Read Through |
|:---|:---|:---|
| 캐시 데이터 채우는 주체 | 애플리케이션 | 캐시 자체 |

#### ✅ 장점

**읽기 작업이 많은 경우** 적합합니다.

#### ❌ 단점

Cache Aside와 비슷하게 **데이터를 처음 요청하면 항상 미스가 발생**합니다.

---

### 4️⃣ Write Behind (Write Back)

> 쓰기 요청은 **캐시까지만** 처리됩니다. 캐시에 데이터가 갱신되면 요청은 완료됩니다.

그리고 **별도의 스케줄 작업** 등으로 캐시의 데이터가 DB에 동기화됩니다.

![2022-10-15-image4](2022-10-15-image4.jpeg)
_Write Behind 전략 흐름도_

#### ✅ 장점

**쓰기 작업이 한 번에 많이 일어날 때** 적합합니다.

예시:
- 🎫 **티켓팅**
- 🎉 **이벤트 참여**
- 🛒 **대규모 프로모션**

한 번에 많이 들어오는 요청들을 캐시에서 처리함으로써 **처리 속도를 향상**시킬 수 있습니다.
그리고 후에 DB에 순차적으로 데이터를 동기화함으로써 **DB의 부하를 줄일 수** 있습니다.

#### ❌ 단점

> ⚠️ 캐시에 데이터를 한 번에 모아뒀다가 후에 순차적으로 처리하기 때문에 그 사이에 **장애가 발생하면 데이터가 유실**될 수 있습니다.
{: .prompt-danger }

캐시에 대해서 알아보았습니다.

글을 작성하면서 캐시 전략이 있다는 것에 놀랐고, 프로젝트에 도입했던 것이 **Cache Aside 전략**이라는 이름이 있다는 것에 두 번 놀랐습니다. 🫢

## 📖 정리 요약

| 전략 | 특징 | 적합한 상황 |
|:---|:---|:---|
| **Cache Aside** | 애플리케이션이 캐시 관리 | 범용적 사용 |
| **Write Through** | 캐시와 DB 동시 쓰기 | 동시성이 중요한 경우 |
| **Read Through** | 캐시가 DB 읽기 관리 | 읽기 작업이 많은 경우 |
| **Write Behind** | 캐시만 쓰고 후에 동기화 | 쓰기가 폭발적인 경우 |

> 💡 **기억하세요!**  
> 상황에 맞는 캐싱 전략을 선택하는 것이 중요합니다.
