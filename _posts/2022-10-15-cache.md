회사 서비스에 [Redis](https://redis.io/)를 도입하게 되었습니다. 데이터를 메모리에 저장해 조회 속도를 높이고 DB 부하를 줄이기 위해서였습니다.

Redis 문서가 잘 되어 있어서 서비스에 도입하는 데까진 문제가 없었습니다. 하지만 캐시가 뭐냐고 물었을 때 간단한 답밖에 하지 못한다는 것을 깨달았습니다. 그래서 정리해보고자 합니다.

---

## 캐시(Cache)란?

컴퓨터 과학에서 데이터나 값을 미리 복사해 놓은 임시 장소를 일컫습니다. 원본 데이터에 접근하는 데 걸리는 시간이 캐시의 접근 시간보다 오래 걸리는 경우나 값을 다시 계산하는 데 걸리는 시간을 단축시키고 싶은 경우 사용합니다.

예를 들자면, 다이소 본점에 가서 물티슈 하나 사는 것보다 집 앞에 있는 다이소에 가는 게 더 빠르게 사 올 수 있습니다.

---

## 캐시에는 어떤 정보를 담아야 할까?

캐시에 담을 정보를 생각할 때 많이 고려하는 법칙이 [파레토의 법칙](https://ko.wikipedia.org/wiki/%ED%8C%8C%EB%A0%88%ED%86%A0_%EB%B2%95%EC%B9%99)입니다. 전체 결과의 80%가 전체 원인의 20%에서 일어나는 현상입니다.

웹 서비스에서는 일부 데이터에 요청이 집중될 수 있다는 관점으로 참고할 수 있습니다. 다만 전체 요청의 80%가 같은 요청이라는 뜻도, 모든 서비스가 정확히 80:20 비율을 따른다는 뜻도 아닙니다. 실제 요청 분포와 조회 비용, 데이터 변경 빈도를 확인한 다음 캐시할 대상을 정해야 합니다.

---

## 지역성 (Locality)

캐시에 담을 정보를 파악하는 데 사용하는 개념입니다.

**시간 지역성 (Temporal Locality)**: 한번 요청받았던 정보는 가까운 시일 내에 또 요청받을 수 있다는 개념입니다. 같은 쿼리로 여러 차례 요청을 받았다면 그 요청만 캐시에 저장해도 성능의 향상을 꾀할 수 있습니다.

**공간 지역성 (Spatial Locality)**: 어떤 데이터에 접근하면 가까운 주소의 데이터에도 곧 접근할 가능성이 높다는 개념입니다. CPU 캐시는 이런 특성을 활용해 캐시 라인 단위로 데이터를 가져옵니다.

캐시가 효율이 좋다면 다 저장하면 되지 않을까? 물론 저장해도 됩니다... 돈이 많다면! 하지만 우린 효율을 따져보고 최상의 결과를 내야 합니다. CACHE IS CASH.

## 캐싱 전략

### Cache Aside (Lazy Loading)

가장 보편적으로 쓰이는 전략입니다.

![2022-10-15-2022-10-15-image1](2022-10-15-image1.jpeg)
_Cache Aside 전략 흐름도_

캐시는 DB와 직접 연결되지 않고 애플리케이션이 주체가 됩니다. 애플리케이션이 요청을 받으면 데이터가 캐시 서버에 있는지 확인합니다. 캐시에 데이터가 있으면(Cache Hit) 바로 반환하고 없으면(Cache Miss) DB에서 데이터를 확인하고 캐시에 저장 후 반환합니다.

**장점**
- 요청받은 데이터만 캐시에 저장하니까 불필요한 데이터를 담지 않음
- 캐시 미스가 발생해도 DB에서 데이터를 읽을 수 있음. 다만 미스가 몰리면 DB 부하가 커질 수 있음

**단점**
- 동시성 문제가 있어요. 캐시에 데이터가 있는 채로 DB의 데이터가 UPDATE 되면 불일치 발생
- 캐시 미스 시 지연 발생

**해결책**
- DB 갱신 시 관련 캐시를 무효화하거나 갱신하고, 만료 기간(TTL)도 설정. TTL은 오래된 값의 유지 시간을 제한하지만 만료 전 불일치나 동시 요청의 경쟁 조건까지 해결하지는 못함
- 캐시 미스 지연은 미리 많이 요청될 것 같은 데이터를 캐시해두면 완화됨

### Write Through

![2022-10-15-image2](2022-10-15-image2.jpeg)
_Write Through 전략 흐름도_

애플리케이션이 직접 바라보는 것은 DB가 아니라 캐시가 됩니다. 데이터가 캐시와 DB에 모두 반영되었을 때 정상적으로 성공했다고 간주합니다.

**장점.** 쓰기 시 캐시와 DB를 함께 갱신하므로 갱신 후 오래된 캐시를 읽는 문제를 줄일 수 있죠. 다만 부분 실패나 캐시를 우회한 DB 변경까지 자동으로 해결되는 것은 아닙니다.

**단점**
- 불필요한 데이터까지도 캐시에 담길 수 있어서 메모리 낭비 가능
- 쓰기 작업이 많은 서비스라면 성능이 오히려 떨어질 수 있음

### Read Through

![2022-10-15-image3](2022-10-15-image3.jpeg)
_Read Through 전략 흐름도_

애플리케이션이 바라보는 것은 DB가 아니라 캐시입니다. 최초 데이터 로딩은 미스가 발생하며, 그때 데이터가 로딩됩니다.

Cache Aside와 뭐가 다르냐면, Cache Aside는 애플리케이션이 캐시 데이터를 채우고 Read Through는 캐시 자체가 채운다는 점이에요.

읽기 작업이 많은 경우 적합합니다.

### Write Behind (Write Back)

![2022-10-15-image4](2022-10-15-image4.jpeg)
_Write Behind 전략 흐름도_

쓰기 요청은 캐시까지만 처리됩니다. 그리고 별도의 스케줄 작업 등으로 캐시의 데이터가 DB에 동기화됩니다.

쓰기 작업을 모아서 DB 부하를 줄일 때 유용합니다. 다만 티켓 재고처럼 유실이나 지연 반영에 민감한 데이터라면 내구성과 일관성을 별도로 설계해야 합니다.

**단점.** 캐시에 데이터를 한 번에 모아뒀다가 후에 순차적으로 처리하기 때문에, 그 사이에 장애가 발생하면 데이터가 유실될 수 있어요.
